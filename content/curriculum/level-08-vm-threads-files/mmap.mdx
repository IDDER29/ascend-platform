So far, files were read with `read()`: a system call copies bytes from the kernel's page cache into your buffer. `mmap` takes another route. It makes part of your address space **be** the file: loading from that memory reads the file, and (if you ask) storing to it changes the file.

## Mapping a file

```c
void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
```

You give a file descriptor, a length and an offset, and the protection you want (`PROT_READ`, `PROT_WRITE`). Usually `addr` is `NULL`, so the kernel chooses where. The kernel only records a new region; nothing is read yet. When you touch a page, the page fault finds the file's page in the page cache (reading it from disk if needed) and maps that very frame into your page table. There's no copy into a buffer: you're looking at the page cache directly.

## Shared or private

The `flags` say what stores do:

- **`MAP_SHARED`:** your stores change the page-cache page, so they reach the file, and every other process mapping or reading that file sees them.
- **`MAP_PRIVATE`:** copy-on-write. Reads come from the file; the first store to a page makes a private copy, and the file never changes.

<details>
<summary>Check your answer</summary>

Through the private mapping, the memory says `Jello, file`, but the file still says `hello, file`: the store went to a private copy. Through the shared mapping, the memory says `Yello, file` and so does the file, read with an ordinary `read()`: the store went into the page cache, which is what `read()` returns too.

Two details in the program: it closes the descriptor straight after `mmap`, and the mapping keeps working, because the mapping holds its own reference to the file. And a shared store is in the page cache, not yet on the disk: the kernel writes it back later, or when you call `msync`.

</details>

<KeyIdea>mmap makes a file part of your address space: page faults bring it in, MAP_SHARED stores change it, and MAP_PRIVATE stores change only your copy.</KeyIdea>

## Anonymous memory

With `MAP_ANONYMOUS` (and no file), mmap gives fresh zero-filled memory, the way earlier lessons got their 1000 pages. glibc's `malloc` does exactly this for large blocks (128 KiB and up by default), and `free` hands them straight back with `munmap`. Small blocks come from the heap, which malloc carves up itself.

## Whole pages

Mappings and protections work on whole pages, because that's what a page-table entry describes. <details>
<summary>Check your answer</summary>

Bytes 99 and 4095 are fine: both are in the first page, which is readable and writable. Byte 4096 is the first byte of the guard page. The page fault finds a region that allows no access, so the kernel sends **SIGSEGV**, and the last line is never printed.

Two lessons hide here. First, an overrun that stays inside the same page is **not caught**: if this program had asked for 100 bytes, writing byte 4095 would still have "worked", silently. Second, guard pages are how overruns get caught on purpose: thread stacks have one below them, and tools like Electric Fence put one after every allocation.

</details>
