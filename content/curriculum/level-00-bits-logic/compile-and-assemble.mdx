In the last lesson the preprocessor turned main.c into plain C text. That text still isn't something a CPU can run. Two more programs turn it into machine code: a <b>compiler</b> and an <b>assembler</b>. You've already been an assembler for the tiny CPU; now you'll meet a real one.

By the end you'll be able to name every stage, stop gcc after any of them, and read what it leaves behind.

## Four stages, one command

When you run `gcc -o prog main.c square.c`, each .c file goes through four stages:

<TruthTable caption='The stages of building a C program' rowsJson='[["stage", "program (gcc 15)", "turns", "into"], ["preprocess", "cc1", "main.c", "C text with headers pasted in"], ["compile", "cc1", "C text", "assembly text (main.s)"], ["assemble", "as", "assembly", "an object file of machine code (main.o)"], ["link", "collect2, which runs ld", "object files", "one executable (prog)"]]' />

In gcc the first two stages happen in the same program, cc1. The first three happen once per .c file; linking happens once for the whole program, and is the next lesson.

## Stop after compiling: gcc -S

`gcc -S square.c` stops after the compile stage and writes square.s. Here is the start of it, from gcc 15.2 on x86-64 Linux:

```
	.file	"square.c"
	.text
	.globl	square
	.type	square, @function
square:
.LFB0:
	.cfi_startproc
	endbr64
	pushq	%rbp
	.cfi_def_cfa_offset 16
	.cfi_offset 6, -16
	movq	%rsp, %rbp
	.cfi_def_cfa_register 6
	movl	%edi, -4(%rbp)
	movl	-4(%rbp), %eax
	imull	%eax, %eax
	popq	%rbp
	.cfi_def_cfa 7, 8
	ret
...
```

It's the same kind of text you wrote for the tiny CPU, for a much bigger CPU. Lines starting with a dot are <b>directives</b>, notes for the assembler rather than instructions: `.globl square` says other files may use this name, and the `.cfi` lines describe the stack for debuggers. The instructions are the rest. `imull %eax, %eax` is the `x * x`. The argument x arrived in register `%edi`, and the result leaves in `%eax`.

This listing was made with no optimisation (the default), so x takes a detour through memory (`-4(%rbp)`) before being multiplied. You'll see what optimisation changes in the last lesson of this section.

## Stop after assembling: gcc -c

`gcc -c square.c` goes one stage further: the assembler turns the text into machine code and stops, leaving <b>square.o</b>, an <b>object file</b>. It's no longer text: `file square.o` describes it as:

```
square.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

"Relocatable" is the important word. The machine code is there, but it isn't finished: main.o calls square without knowing where square will end up, and neither file knows where it will be loaded. Filling in those gaps is the linker's job.

<KeyIdea>The compiler turns C into assembly for one CPU. The assembler turns assembly into an object file: machine code with gaps still to fill.</KeyIdea>

## One command, every stage

Normally you never see .s or .o files: gcc writes them to temporary files and deletes them. gcc is a <b>driver</b> that runs the real tools in order. Two flags let you watch:

- `gcc -save-temps -o prog main.c square.c` keeps every in-between file. In the folder afterwards: `prog-main.i` (preprocessed, 856 lines), `prog-main.s`, `prog-main.o`, the same three for square, and `prog`.
- `gcc -v -o prog main.c square.c` prints each program it runs. Trimmed to just the program names, gcc 15 on this system ran `/usr/libexec/gcc/x86_64-linux-gnu/15/cc1` and `/usr/bin/x86_64-linux-gnu-as` once per file, then `/usr/libexec/gcc/x86_64-linux-gnu/15/collect2` once to link.

Paths and file names differ between systems and gcc versions; the stages don't.
