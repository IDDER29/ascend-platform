This optional project builds a tiny library of subroutines. The main program is given; the routines are stubs that return straight away. Fill them in until the output is 42 and then 25.

The library's rules (its "calling convention"): arguments come in R0 and R1, the result goes back in R0, and a routine that uses R2 saves and restores it.

<TinyCpu2 editable caption='A subroutine library' programJson='["LDI R0, 6", "LDI R1, 7", "CALL mul", "OUT R0", "LDI R0, 5", "CALL square", "OUT R0", "HALT", "mul: RET", "square: RET"]' goalJson='{"out":[42,25]}' />

## Part 1: Multiply by adding

Write `mul`: R0 = R0 × R1, for R1 of at least 1. The CPU can only add, so add R0 to a running total R1 times. Use R2 for the total, and save R2 first with PUSH, restoring it with POP before RET.

<details>
<summary>Check your answer</summary>

```
mul: PUSH R2
LDI R2, 0
mloop: ADD R2, R0
DEC R1
JNZ mloop
MOV R0, R2
POP R2
RET
```

With R1 = 0 it would count down from 0, wrap to 255 and add 256 times, which is why the rule says "at least 1". A library has to say what it expects.

</details>

## Part 2: A subroutine that calls another

Write `square`: R0 = R0 × R0, using `mul`.

<details>
<summary>Check your answer</summary>

```
square: MOV R1, R0
CALL mul
RET
```

Step through it and watch SP: main's CALL pushes one return address (SP goes from 0xF0 to 0xEF), square's CALL pushes a second (0xEE), mul's PUSH R2 a third (0xED). Then each POP and RET takes them back off in the opposite order, and SP ends at 0xF0 again.

</details>

<KeyIdea>The stack lets calls nest: each CALL leaves its own way back, and each RET takes the most recent one.</KeyIdea>

## Done when

The output is 42 and then 25, SP is back at 0xF0 when it halts, and you can say what each routine takes, returns and changes.
