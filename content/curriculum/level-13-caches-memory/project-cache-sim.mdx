In this project you build intuition with a simulator: a C program that plays a trace of addresses through a set-associative cache. You'll check it against the Cache Lab, then use both to explain a surprising result and fix it.

## Part 1: The simulator

The program takes the cache's size, line size and ways on its command line, and reads `R address` lines. For each access it:

- splits the address into offset, index and tag;
- looks for the tag in that set's ways;
- on a miss, evicts the least recently used way, and counts the miss as compulsory if this line has never been seen before.

The first trace walks a 16 by 16 matrix of 4-byte ints **row by row**, from address 0x1000, through a 512-byte, 2-way cache with 32-byte lines. Predict the hits and misses.

<CRun program="architect/cachesim-rows" caption='Row by row' predict />

<details>
<summary>Check your answer</summary>

256 accesses, 224 hits and 32 misses, all of them compulsory: 87.5% hits. Each 32-byte line holds 8 ints, so a row walk misses on the first int of each line and hits on the next 7. The matrix is 1 KiB, which is 32 lines and twice the cache, but a row walk never comes back to a line, so evicting old lines costs nothing. That's spatial locality at work.

</details>

## Part 2: The same data, two walks

Now the same matrix **column by column**: all 16 rows of column 0, then column 1, and so on. Same cache. Predict the hit rate before you run it.

<CRun program="architect/cachesim-cols" caption='Column by column' predict />

<details>
<summary>Check your answer</summary>

**0 hits.** Every one of the 256 accesses misses.

- **Ideally:** a column walk touches 16 lines, one per row, and then the next column needs the same 16 lines again (column 1 is in the same lines as column 0). 16 lines of 32 bytes is 512 bytes, so they'd just fit.
- **But:** each row is 64 bytes, two lines, so going down a column jumps two lines at a time. The index is the line number mod 8, so the 16 rows land in only sets 0, 2, 4 and 6, four lines per set, and each set has only 2 ways. LRU throws each line out before the walk comes back to it.

These are **conflict misses**: the data would fit, but the mapping crams it into too few sets.

</details>

## Part 3: Fix it two ways

**Change the layout.** Pad each row to 17 ints, 68 bytes, so moving down a column no longer jumps a whole number of lines:

<CRun program="architect/cachesim-cols-padded" caption='Column by column, rows padded to 17 ints' predict />

**Change the cache.** In the lab below the same unpadded column walk starts at 0% hits. Change the cache's ways or size to reach at least 85% hits. Before each change, predict the result.

<details>
<summary>Check your answer</summary>

**Padding** gives 167 hits, 89 misses: 65.2%. The rows now map to all 8 sets, so the 16 lines of a column are spread out instead of piled into four sets. It isn't perfect, because those 16 lines are the whole cache, and the next column's lines arrive before every line has been reused.

**Changing the cache:**

- **16 ways:** the cache is fully associative (one set of 16 lines). All 16 lines of a column fit, and every column after the first hits: 224 hits, 87.5%.
- **1 KiB with 2 ways:** 16 sets, so the rows use 8 sets with 2 lines each. That fits exactly, and you also get 87.5%.
- **4 ways, 512 bytes:** still 0%. With 4 sets the rows land in only 2 of them, 8 lines per set, still too many for 4 ways. More ways only helps once there are enough of them for the lines that collide.

In real code you can rarely change the cache, but you can change the layout or the loop order. That's why matrix code is written to walk rows in C.

</details>

## Part 4: Trust, but check

The C simulator and the Cache Lab are separate implementations, one in C, one in TypeScript. On the row walk, column walk and padded walk they agree exactly: 224, 0 and 167 hits. Why is it worth having both, and what would you test next if they disagreed?

<details>
<summary>Check your answer</summary>

Two independent implementations rarely share the same bug, so agreement is strong evidence both apply the rules correctly. If they disagreed, compare them access by access on a tiny trace: the first access where the hit or miss differs points to the bug. Typical culprits are the address split (off by one bit), LRU bookkeeping (updating the time on a hit), or which way is chosen when a set has an empty way. Architects check a new design against a reference model in exactly this way.

</details>

<KeyIdea>Caches reward the right walk through memory. When the data fits but still misses, look at the mapping: too many lines fighting over too few sets. Fix the layout, the loop order or the cache, then measure.</KeyIdea>
