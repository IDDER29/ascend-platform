All through Foundations you've traced programs on the tiny CPU. This lesson reads the real thing: assembly that gcc wrote for a real C function, for a real CPU. Nothing below is made up or tidied by hand: it's exactly what gcc printed, kept with a record of how it was made.

By the end you'll be able to follow a real listing line by line, explain why optimisation changes it so much, and say which parts would change on another compiler or CPU.

## The evidence

Here is one small function, `sum_to`, which adds 1 + 2 + ... + n, compiled by gcc 15.2 for x86-64 Linux twice: with optimisation off (-O0) and on (-O2).

<CompilerOutput evidence="sum-to-n" fn="sum_to" />

Both programs print 55. They don't look alike at all.

## Optimisation off: everything goes through memory

At -O0 gcc translates each line of C plainly, and gives every variable a home in memory, a <b>stack slot</b> at a fixed distance below `%rbp`:

<TruthTable caption='Where each variable lives at -O0' rowsJson='[["variable", "home", "set up by"], ["n", "-20(%rbp)", "movl %edi, -20(%rbp)"], ["total", "-8(%rbp)", "movl $0, -8(%rbp)"], ["i", "-4(%rbp)", "movl $1, -4(%rbp)"]]' />

Then the loop. The test is at the bottom: `.L2` compares i with n, and `jnb .L3` ("jump if not below") goes back to the body while n is not below i. The body, `.L3`, loads i into `%eax`, adds it to total in memory (`addl %eax, -8(%rbp)`), and adds 1 to i in memory. At the end, `movl -8(%rbp), %eax` puts total where the caller expects the result.

It's the same shape as the loops you wrote for the tiny CPU: a compare, a conditional jump back, and a variable kept in memory and loaded when needed.

## Optimisation on: variables move into registers

At -O2, look for `-8(%rbp)` or `-4(%rbp)`: they're gone. total lives in `%edx` and i in `%eax` for the whole function. Those named variables never get a memory address at all.

The loop changed too. Its body is now:

```
.L3:
	leal	1(%rdx,%rax,2), %edx
	addl	$2, %eax
	cmpl	%eax, %edi
	jnb	.L3
```

`leal 1(%rdx,%rax,2), %edx` computes total + 2 × i + 1, which is total + i + (i + 1): two numbers added in one instruction. Then i goes up by 2. The loop runs half as many times. The instructions before `.L3` handle the edge cases this trick needs: n of 0 (jump to `.L4`, return 0) and an odd count of numbers.

<KeyIdea>C promises what a program computes, not how. A named variable may live in memory, only in a register, or nowhere at all.</KeyIdea>

## The same answer, a different program

The -O2 version of `main`, in the same evidence file (content/evidence/sum-to-n/O2.s), goes further:

```
main:
	endbr64
	subq	$8, %rsp
	movl	$55, %edx
	movl	$.LC0, %esi
	xorl	%eax, %eax
	movl	$2, %edi
	call	__printf_chk
	xorl	%eax, %eax
	addq	$8, %rsp
	ret
```

There's no call to sum_to. gcc worked out `sum_to(10)` while compiling and put 55 in directly (`movl $55, %edx`). It also replaced printf with `__printf_chk`, a checked version this system's gcc uses by default. The output is still 55, which is all C promises.

## What depends on what

Almost everything in these listings is a choice made by someone, not a law:

- **The compiler and its flags** decide the instructions: gcc 15.2 at -O2 unrolled the loop; another gcc version, or clang, may not.
- **The target CPU** decides the instruction set: these are x86-64 instructions (`leal`, `jnb`); an ARM CPU would get completely different ones from the same C.
- **The calling convention (ABI)** decides where arguments and results go: on x86-64 Linux (the System V ABI), the first argument arrives in `%edi` and the result leaves in `%eax`. 32-bit x86 Linux passes arguments on the stack instead: the same function compiled with `-m32 -O2` (kept in the same evidence folder as O2-m32.s) starts by reading n with `movl 8(%esp), %ecx`.

Only the C result, 55, is guaranteed everywhere.

<details>
<summary>Check your answer: name two ways this differs from the tiny CPU.</summary>

Any two of these:

- x86-64 has many registers (16 general-purpose, 64 bits wide); the tiny CPU version 2 has four 8-bit ones.
- x86-64 instructions vary in length (1 to 15 bytes); the tiny CPU's are always 2 bytes.
- x86-64 compares numbers by size (`jnb`: not below) using its carry flag; the tiny CPU can only test for equality.
- Here a compiler chose the instructions and could reorder or remove work; on the tiny CPU you wrote every instruction yourself.

</details>

To try other compilers and CPUs without installing anything, Compiler Explorer (godbolt.org) shows the assembly for any C you paste in. Its output will differ from this lesson's whenever the compiler, version, flags or target differ, which is exactly the point.
