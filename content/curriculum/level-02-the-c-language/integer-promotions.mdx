C never does arithmetic on mixed or small types as written. Before any operator runs, it quietly converts its operands. Most of the time you never notice; when you do, the results look impossible. Two rules explain all of it.

## Rule 1: small types become int

The **integer promotions**: any `char`, `signed char`, `unsigned char`, `short` or `unsigned short` in an expression is converted to `int` before the arithmetic happens. (In the rare case that `int` can't hold all its values, it becomes `unsigned int`; on any mainstream system `int` can.)

- `sizeof(x + y)` is 4: the expression has type `int`, whatever the operands were.
- 200 doesn't fit in a `char`, which is signed on x86-64 Linux (range -128 to 127). The conversion gives 200 - 256 = -56. Whether plain `char` is signed is up to the platform; on ARM Linux it's unsigned and you'd see 200. That's why byte data belongs in `unsigned char` or `uint8_t`.

</details>

## Rule 2: mixed types meet at a common type

The **usual arithmetic conversions** pick one type for both operands of `+`, `<`, `==` and the rest. For integers, after promotions: if one operand is unsigned and at least as wide as the other, the signed one is converted to unsigned.

It prints "-1 is not less than 1u". `a` is `int` and `b` is `unsigned int`, so `a` is converted to `unsigned int`. In two's complement, -1 is all 32 bits set, which read as unsigned is 4294967295. And 4294967295 is not less than 1.

gcc saw it coming: `-Wextra` turns on `-Wsign-compare`, "comparison of integer expressions of different signedness". Take that warning seriously. The usual fix is to keep both sides signed, or to check the signed value for negative before comparing.

</details>

<KeyIdea>Small integer types are promoted to int; when signed meets unsigned of the same width, the signed value becomes unsigned. Most "impossible" integer results are one of these two rules.</KeyIdea>

## Unsigned wraps, signed overflows

The two kinds of integer behave differently at their limits:

<CRun program="c-language/ip-overflow" caption='One past the maximum' />

`UINT_MAX + 1` is exactly 0: unsigned arithmetic is defined to wrap around, modulo 2 to the power of the width. `INT_MAX + 1` is **undefined behaviour**. This build used `-fsanitize=undefined`, so UBSan reported the overflow while the program ran. It printed -2147483648 here, but nothing guarantees that: an optimising compiler may assume signed overflow never happens. For example, it may turn `i + 1 > i` into "always true", or remove a check you wrote after the overflow.

If you need wrap-around, use an unsigned type. If you need to detect overflow, check before the operation (`if (i > INT_MAX - 1)`), or use gcc's `__builtin_add_overflow`.

## The size_t trap

`strlen` returns `size_t`, an unsigned type (64 bits on x86-64 Linux). This check was meant to ask "is the name longer than 5 characters?". What does it print?

<details>
<summary>Check your answer</summary>

The two checks disagree: the first says the name is longer than 5, the second says it isn't. `strlen(name) - 5` is 2 - 5 in `size_t`, which wraps to 18446744073709551613, and that is certainly greater than 0. The second test, `strlen(name) > 5`, never subtracts, so it's right: "not longer than 5".

The rule of thumb: with unsigned types, move the subtraction to the other side as an addition (`a > b + 5` rather than `a - b > 5`), or compare directly. The same trap hides in loops like `for (size_t i = n - 1; i >= 0; i--)`, which never ends: an unsigned `i` is always at least 0.

</details>
