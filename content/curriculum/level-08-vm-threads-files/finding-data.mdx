The last lesson said the inode records where a file's data is. This one opens that up: how the file system turns "byte 10000 of this file" into "block 42847346 on the disk".

## Blocks

A file system divides its disk into **blocks**, usually 4096 bytes on ext4. A file's bytes are cut the same way: bytes 0 to 4095 are its **logical block** 0, bytes 4096 to 8191 are logical block 1, and so on. Finding a byte is two steps:

1. **Offset to logical block:** `offset / 4096`, and the remainder is the position inside the block. That's arithmetic.
2. **Logical block to disk block:** that's what the inode's map is for.

## Block pointers and extents

The classic Unix answer to step 2 is a list of **block pointers** in the inode: one disk-block number per logical block. To fit big files, the inode holds a few direct pointers and then pointers to blocks full of more pointers (indirect, double-indirect blocks), a small tree. That works, but a 1 GiB file needs 262144 pointers, even when its blocks sit side by side on the disk.

ext4 instead stores **extents**: runs of the form "logical blocks L to L+n-1 are at disk blocks P to P+n-1". A file written in one go is often a single extent. `filefrag -v` lists a file's extents. Here it is on a 1 MB file on this machine's ext4 disk:

```
$ filefrag -v big.bin
Filesystem type is: ef53
File size of big.bin is 1000000 (245 blocks of 4096 bytes)
 ext:     logical_offset:        physical_offset: length:   expected: flags:
   0:        0..     244:   42290426..  42290670:    245:             last,eof
big.bin: 1 extent found
```

245 blocks, one extent: logical 0 to 244 sit at disk blocks 42290426 to 42290670. Three numbers describe the whole file. (`ef53` is ext4's magic number. Your block numbers will differ.)

When a file has many extents, ext4 keeps them in a small tree in the inode, so finding the extent for a block is quick even for huge files.

## From offset to disk block

This file on ext4 has three extents, because it was written in three separate places:

```
$ filefrag -v sparse.bin
Filesystem type is: ef53
File size of sparse.bin is 4100096 (1001 blocks of 4096 bytes)
 ext:     logical_offset:        physical_offset: length:   expected: flags:
   0:        0..       3:   42847344..  42847347:      4:
   1:      100..     101:   21860959..  21860960:      2:   42847444:
   2:     1000..    1000:   22953284..  22953284:      1:   21861859: last,eof
sparse.bin: 3 extents found
```

Byte 10000 is in logical block 2 (10000 / 4096 = 2, remainder 1808). Extent 0 covers logical blocks 0 to 3 starting at disk block 42847344, so block 2 is at 42847344 + 2 = **42847346**. Byte 204800 is in logical block 50, which no extent covers: it's in a **hole**.

<KeyIdea>Finding data is offset / block size to get the logical block, then the inode's extents to get the disk block. Logical blocks no extent covers are holes.</KeyIdea>

## Holes

`sparse.bin` is 4100096 bytes long, yet only 7 of its 1001 blocks were ever written. The others are **holes**: no extent, no disk block, nothing stored. Reading a hole returns zeros. `ls -ls` shows the space really used, in KiB, in its first column:

```
$ ls -ls sparse.bin
28 -rw-rw-r-- 1 learner learner 4100096 Oct 31 13:13 sparse.bin
```

A program can ask where the data is, without knowing the file system: `lseek` with `SEEK_DATA` jumps to the next byte that has data, and `SEEK_HOLE` to the next hole. This program writes the same pattern (blocks 0 to 3, 100 and 101, and 1000), then asks. Predict the space used and the data ranges.

Tools like `cp --sparse` and `tar` use it to copy only the data. Copying a sparse file with a plain loop of `read` and `write` fills every hole with real zero blocks.
