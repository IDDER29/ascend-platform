An optimising compiler makes a bargain with you: it assumes your program **never has undefined behaviour**, and in exchange it makes the program fast. That assumption isn't only used to skip work. The optimiser **reasons backwards** from it: "if this line ran with that value, the behaviour would be undefined; so that value never happens here." Every conclusion like that can remove code.

You've already seen one case in Signed overflow and shifts: `x + 1 < x` can only be true if `x + 1` overflows, which is undefined, so gcc replaced the whole test with "false". This lesson shows three more, all observed with this machine's gcc. Remember that every output from a program with undefined behaviour is what this compiler did once, not a promise.

## A search that always succeeds

`in_table` looks for `v` in a 4-element table, but its loop runs one step too far: `i <= 4` reads `table[4]`. The input is 99, which isn't in the table. Predict the -O0 run.

Now the same source and input with -O2.

<CRun program="c-contract/assume-table-O2" caption='in_table(99), compiled with -O2' predict />

<details>
<summary>Check your answer</summary>

-O0 says 0: on its last step the loop read whatever happened to sit in memory after the table, which wasn't 99, so it found no match and returned 0.

-O2 says 1: 99 is "in the table". Here's gcc's reasoning. On the iteration with `i == 4`, `table[4]` would be read, and reading past the end of an array is undefined. So that iteration never happens. The only way the loop can stop before `i` reaches 4 is `return 1`. So the function always returns 1. This is the entire function as gcc compiled it at -O2:

```
in_table:
	endbr64
	movl	$1, %eax
	ret
```

No loop, no table, no comparison. And no warning, either: `-Wall -Wextra` said nothing.

</details>

The sanitizer catches it. With `-fsanitize=undefined`, gcc instruments array accesses and reports the bad index at run time:

<CRun program="c-contract/assume-table-ubsan" caption='The same program with -O2 -fsanitize=undefined' />

UBSan reports `index 4 out of bounds for type 'int [4]'` at the exact line. The output also went back to 0, because the checks change what the optimiser can assume. Fix the loop to `i < 4` and all three builds agree.

## A null check that disappears

This function reads `*p`, then checks `p` for null:

```c
int read_or_default(const int *p) {
    int value = *p;
    if (p == NULL) {
        puts("null pointer, using the default");
        return -1;
    }
    return value;
}
```

This is real gcc 15.2 output for it (`gcc -std=c17 -S -fno-asynchronous-unwind-tables`), first at -O0:

```
read_or_default:
	endbr64
	pushq	%rbp
	movq	%rsp, %rbp
	subq	$32, %rsp
	movq	%rdi, -24(%rbp)
	movq	-24(%rbp), %rax
	movl	(%rax), %eax
	movl	%eax, -4(%rbp)
	cmpq	$0, -24(%rbp)
	jne	.L2
	leaq	.LC0(%rip), %rax
	movq	%rax, %rdi
	call	puts@PLT
	movl	$-1, %eax
	jmp	.L3
.L2:
	movl	-4(%rbp), %eax
.L3:
	leave
	ret
```

and at -O2:

```
read_or_default:
	endbr64
	movl	(%rdi), %eax
	ret
```

Where did the check go?

<details>
<summary>Check your answer</summary>

Dereferencing a null pointer is undefined (C17 6.5.3.2p4). `movl (%rdi), %eax` reads `*p` first, so after that line gcc may assume `p` isn't null. The check `p == NULL` can then never be true, so gcc deletes it, with the `puts` and the `return -1` inside it. At -O0 the check is still there, but it comes too late to help: the read on the line before has already crashed for a null `p`.

The fix is to check before the first use:

```c
int read_or_default(const int *p) {
    if (p == NULL) {
        puts("null pointer, using the default");
        return -1;
    }
    return *p;
}
```

gcc -O2 keeps that check (`testq %rdi, %rdi` then `je` to the default path), because now it's reached before anything is assumed.

</details>

gcc calls this optimisation `-fdelete-null-pointer-checks`, and it's on by default. The Linux kernel builds with `-fno-delete-null-pointer-checks`, after a real security bug in which exactly this pattern removed a check. In your own code, ordering the check correctly is the fix; the flag is a safety net.

<KeyIdea>The optimiser reasons from 'undefined behaviour never happens'. A check that comes after the undefined operation it was meant to prevent can always be proven false, and deleted.</KeyIdea>

## Loops that may be assumed to end

C17 6.8.5p6 gives compilers one more assumption. A loop whose controlling expression isn't a constant, and whose body does no input or output, no `volatile` accesses and no atomic or synchronising operations, **may be assumed to terminate**. (A loop written `while (1)` doesn't qualify, because 1 is a constant expression.)

`search` loops until `n * n` ends in the digit 2, which no square ever does, so it never ends. It does no I/O, so it qualifies. Predict the run.

<details>
<summary>Check your answer</summary>

It never finishes: the run was stopped after 3 seconds, with nothing printed. gcc is *allowed* to assume the loop ends, but by default, in C, it doesn't use that freedom. The loop is still in the -O2 code.

</details>

gcc has a flag for using it, `-ffinite-loops`, which gcc turns on by default only for C++ (C++11 or later, at -O2 and above). Here is the same C with it turned on:

<CRun program="c-contract/assume-loop-finite" caption='-O2 -ffinite-loops' />

It printed `found: 1` at once. `search` can only end by returning 1, and the compiler may now assume it ends, so `main` uses 1 without ever running the loop. The same source, with a different but standard-conforming assumption, prints a result from a search that can never finish. A loop meant to wait forever should have a constant condition (`for (;;)`) or a side effect, such as a `volatile` read, so no compiler may assume it away.

## Protecting yourself

The optimiser's assumptions are only dangerous when your code has undefined behaviour, so:

- **Find the undefined behaviour.** Test with `-fsanitize=undefined,address`, and read every warning from an optimised build (`-O2 -Wall -Wextra`).
- **Order checks before uses**: bounds before indexing, null before dereferencing, overflow before the arithmetic.
- **Use flags as safety nets, not fixes**: `-fwrapv`, `-fno-strict-aliasing`, `-fno-delete-null-pointer-checks` make gcc assume less, but the code is still not portable C.

## Try it

`name_length` is called with `NULL` when a user has no name. Which line makes the check useless, and how do you fix it?

```c
#include <stddef.h>
#include <string.h>

size_t name_length(const char *name) {
    size_t length = strlen(name);
    if (name == NULL) {
        return 0;
    }
    return length;
}
```

<details>
<summary>Check your answer</summary>

`size_t length = strlen(name);` comes first. `strlen(NULL)` is undefined (it must read the string), so after that line the compiler may assume `name` isn't null and delete the check, and in any case the program has already crashed or misbehaved before reaching it. Move the check first:

```c
size_t name_length(const char *name) {
    if (name == NULL) {
        return 0;
    }
    return strlen(name);
}
```

</details>
