Big-O counts steps as if every step cost the same. On real hardware they don't: a read that hits the cache takes a few cycles, and one that has to go to main memory can take hundreds. In Machine & Memory you met cache lines and locality. Here you'll measure what they do to data structures.

## How to read the timings

The programs below time themselves with `clock_gettime(CLOCK_MONOTONIC, ...)`, built with `-O2`. The times are real, from one run on the build machine. **They vary**: by machine, by run and by what else the computer is doing. Your numbers will differ. Read the *ratios*, not the milliseconds. Each program also prints a sum, so you can see both versions do the same work (and so the compiler can't skip the loop).

Counting cache misses directly with `perf stat -e cache-misses` needs permission to read the CPU's performance counters. On the build machine that's switched off for ordinary users, so this lesson measures time instead. On your own Linux machine, try perf on these programs; you may need `sudo`.

## Rows and columns

C stores a 2D array **row after row**: `grid[r][c]` is followed in memory by `grid[r][c + 1]`. This program sums a 2048 by 2048 grid of ints (16 MB, far bigger than the caches) twice: row by row, then column by column. Same additions, same Big-O. Predict which is faster, and by roughly how much.

<details>
<summary>Check your answer</summary>

Row order was about 7 times faster here (2.4 ms against 16.5 ms). Memory moves between RAM and cache in **cache lines** of 64 bytes. In row order, one line holds 16 consecutive ints, so one slow fetch serves 16 additions, and the **prefetcher**, the hardware that spots a steady stride and fetches ahead, keeps the next lines coming. In column order each step jumps a whole row, 8 KB, landing in a different line every time. Most of each fetched line is wasted, and the stride defeats much of the prefetching.

The fix costs nothing: make the inner loop run over the last index.

</details>

## Arrays and linked lists

A linked list does the same O(n) walk as an array, but each step follows a pointer to wherever the next node happens to be. This program sums 4 million values three ways: in an array; in a linked list whose nodes lie in memory in list order; and in the same list after shuffling the links so each `next` points somewhere far away. Predict the order of the three times.

<details>
<summary>Check your answer</summary>

Here the array took 1.6 ms, the in-order list 10.3 ms, and the scattered list 671.6 ms, about 400 times slower than the array for exactly the same additions.

- The **array** packs 16 ints per cache line, the prefetcher streams them in, and the compiler can use vector instructions that add several at once.
- The **in-order list** still moves forward through memory, so the prefetcher helps, but each node is 16 bytes (a value, padding and a pointer), so only 4 nodes fit in a line, and each step must wait for the pointer before it knows where to go next.
- The **scattered list** misses the cache on almost every node, and each miss must finish before the next address is known, so no prefetching can help.

Lists built over time by `malloc` often end up scattered like this. That's why, for most uses, a dynamic array beats a linked list in practice, even where the list's Big-O looks the same or better.

</details>

<KeyIdea>Memory arrives in 64-byte cache lines. Layouts that use every byte of each line, in order, are fast; layouts that jump around, or that load bytes they don't need, are slow, whatever their Big-O says.</KeyIdea>

## Array of structs, or struct of arrays

A simulation keeps 2 million particles, each with a position, a velocity, a mass and an id: 64 bytes. There are two ways to store them:

- an **array of structs (AoS)**: `struct particle p[N]`, each particle's fields together;
- a **struct of arrays (SoA)**: one array per field, `x[N]`, `y[N]` and so on.

This loop needs only one field: the average x. Predict which layout is faster.

<CRun program="data-structures/cache-aos-soa" caption='One field from 2 million particles' predict />

<details>
<summary>Check your answer</summary>

The struct of arrays was about 3 times faster here (2.5 ms against 8.1 ms). With AoS, every 64-byte line fetched holds one whole particle, and the loop uses 8 of its bytes: seven eighths of the memory traffic is wasted. With SoA, the x values are packed together: every byte fetched is an x the loop needs.

AoS isn't wrong, though. When a loop uses **all** the fields of each particle together, AoS keeps them in one line, and SoA has to fetch from eight places. Choose the layout from how the data is *used*: game engines and numerical code often use SoA for their hot loops for exactly this reason.

</details>
