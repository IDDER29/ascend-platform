This optional project compares the same `sum_to`, compiled by the same gcc at -O2, for two targets: 64-bit x86 (as before) and 32-bit x86 (`-m32`).

## Part 1: Where does n come from?

In each listing, find where the function first reads n.

<details>
<summary>Check your answer</summary>

On 64-bit, n is already in `%edi` when the function starts (`testl %edi, %edi`). On 32-bit, the function loads it from the stack: `movl 8(%esp), %ecx`. By then the function has pushed `%ebx`, so `0(%esp)` holds the saved `%ebx`, `4(%esp)` the return address, and `8(%esp)` the argument. The i386 convention passes arguments on the stack; x86-64's passes the first ones in registers.

</details>

## Part 2: What else changed?

Find two more differences between the listings.

<details>
<summary>Check your answer</summary>

- The 32-bit version saves and restores `%ebx` (`pushl %ebx` … `popl %ebx`): it needs one more register, and the convention says the caller expects `%ebx` unchanged. 64-bit has spare registers it may use freely.
- The 32-bit version has no `endbr64` line, which belongs to a 64-bit control-flow protection feature.
- The loop itself is the same idea on both: two numbers per trip with `leal 1(%edx,%eax,2)`.

</details>

## Part 3: What did C promise?

Which of these does C itself guarantee: the result for n = 10; that n arrives in a register; that `%ebx` is saved?

<details>
<summary>Check your answer</summary>

Only the result (55). Where arguments arrive and which registers must be saved are the target's calling convention: rules that compilers for that target agree on, so code from different compilers can call each other.

</details>
