The translator turns the tiny language into tiny CPU assembly. In this project you do the same job by hand, compare your work with the translator's, then find a bug in a broken translator.

## Part 1: Translate it yourself

This program adds 4 + 3 + 2 + 1. Write your own assembly for it in the lower box (keep the total in a register if you like), and make it output 10. The upper half shows the translator's version for comparison; try not to copy it.

<TranslatorLab handwritten caption='Your translation and the translator&#39;s' startJson='["var n = 4;", "var t = 0;", "while (n != 0) {", "  t = t + n;", "  n = n - 1;", "}", "output(t);"]' handJson='["; your translation goes here", "HALT"]' />

<details>
<summary>Check your answer</summary>

A short hand translation keeps both values in registers:

```
LDI R0, 4        ; n
LDI R1, 0        ; t
loop: ADD R1, R0 ; t = t + n
DEC R0           ; n = n - 1, and sets Z
JNZ loop         ; while n != 0
OUT R1
HALT
```

7 instructions, 16 steps. The translator's version is 19 instructions and runs 58 steps for the same answer. It's correct, just not careful: it does the same few moves for every line.

</details>

## Part 2: Read the translator

Look at the translator's output above. Find the label at the top of the loop, the test, and the jump back. Why does it load n from memory again in the test, when it stored n just before?

<details>
<summary>Check your answer</summary>

`while1:` marks the top. `LDA R0, [0x80]`, `CMPI R0, 0`, `JZ endwhile1` is the test: jump out when n is 0. Then comes the body, `JMP while1`, and `endwhile1:` after it.

It reloads n because it translates each line on its own, never remembering what a register already holds. That keeps the translator short and always correct; remembering values across lines is what an optimising compiler adds, and gcc at -O2 does exactly that.

</details>

## Part 3: Two variables, one box

A classmate's translator has a bug: it gave both n and t the box 0x80. With their translator, the program from part 1 outputs 0, not 10. Explain why from the program, without running anything.

<details>
<summary>Check your answer</summary>

`var n = 4` stores 4 in 0x80; then `var t = 0` stores 0 in 0x80 too, which also makes n 0. The loop's first test reads 0x80, finds 0, and jumps past the loop. Nothing is added, and t (the same box, still 0) is output. One wrong address in the allocator breaks every program with two variables. The fix is to give each new variable the next free box: 0x80, 0x81, and so on.

</details>

## Part 4: Where the language stops

Change `t = t + n;` to `t = t * n;` in the upper box. What does the translator say, and how would you multiply in this language instead?

<details>
<summary>Check your answer</summary>

It refuses with "this language only has + and - (multiply with a loop)". A real compiler also stops with an error rather than guessing. To multiply, add one number to a total, the other number of times, in a while loop: the same idea as the multiply you wrote in assembly.

</details>

<KeyIdea>A compiler is a careful, mechanical translator. A simple one is correct but wasteful; optimisation is what makes its output as good as a careful hand translation.</KeyIdea>
