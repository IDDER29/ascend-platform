Everything so far assumed programs do what they're meant to. They don't. Programs have bugs, follow bad pointers and run off the ends of arrays. Some are written to cause harm. A system shared by many programs has to survive all of them.

## Programs can be wrong

This program follows a pointer to address 0x10, which isn't part of its memory:

```c
#include <stdio.h>

int main(void) {
    int *p = (int *)0x10;
    printf("about to write through %p\n", (void *)p);
    fflush(stdout);
    *p = 42;
    printf("never printed\n");
    return 0;
}
```

On Linux (gcc 15.2, x86-64, run from bash followed by `echo "exit status $?"`; messages differ by system):

```
about to write through 0x10
bash: line 1: 538167 Segmentation fault         (core dumped) ./crash
exit status 139
```

The MMU found no mapping for 0x10 in this process's map, the CPU trapped into the kernel, and the kernel ended the program. Nothing else on the machine noticed.

## Programs can be hostile

This one tries something worse: talking to a hardware I/O port directly, with the x86 `outb` instruction:

```c
#include <stdio.h>

int main(void) {
    printf("about to talk to I/O port 0x80 directly\n");
    fflush(stdout);
    __asm__ volatile ("outb %%al, $0x80" : : "a"(0));
    printf("never printed\n");
    return 0;
}
```

```
about to talk to I/O port 0x80 directly
--- SIGSEGV {si_signo=SIGSEGV, si_code=SI_KERNEL, si_addr=NULL} ---
+++ killed by SIGSEGV (core dumped) +++
```

`outb` is a **privileged** instruction. In user mode, the CPU refuses it and traps to the kernel (`SI_KERNEL`: the kernel sent this signal), which stops the program. If any program could drive devices, any program could wipe the disk or read the keyboard of another user.

Notice the contrast with the tiny CPU: its `OUT` works for every program, because it has no user mode and no kernel. That's fine for one trusted program at a time, and impossible for a shared machine.

## The kernel checks what it's given

A system call is a doorway into the kernel, which runs with full privilege. So the kernel treats every argument as suspect: is this file descriptor really open in this process? Is this buffer address really inside this process's memory?

## Checking bounds

The kernel can only check what crosses into it. Inside a program, C itself doesn't check array bounds: writing `a[9]` in an array of 4 just writes to whatever is 36 bytes past the start. If that's still the program's own memory, nothing stops it, and it silently corrupts another variable. Many security holes start exactly here.

Defences come in layers: languages that check bounds, compiler tools such as `-fsanitize=address` that catch the mistake while testing, and the OS limits (separate address spaces, no-execute memory, randomised addresses) that make what's left harder to exploit.

## Failures and recovery

Not every failure is a bug. Disks fail, power goes, networks drop. Systems plan for it:

- **Contain it.** A crashed process is cleaned up by the kernel (memory freed, files closed), and others keep running.
- **Report it.** System calls return errors; programs return exit codes (139 above means "killed by signal 11, SIGSEGV").
- **Make it recoverable.** Data in RAM is lost on a power cut. Programs that must not lose data call `fsync` to force it to the disk before saying "saved", and file systems keep a journal so they can repair themselves after a crash.
