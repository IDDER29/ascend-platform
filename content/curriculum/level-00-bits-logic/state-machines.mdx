A counter always does the same thing: add 1. Many machines need to follow different steps depending on what happens: a turnstile, a traffic light, the control unit of a CPU. These are <b>state machines</b>, and they're built from exactly the two pieces you already have: a register to hold the state, and gates to work out the next one.

By the end you'll be able to describe a machine as a table of states, encode the states in bits, and build it in a clocked circuit.

## States, transitions, outputs

A <b>finite state machine</b> is described by four things:

- its <b>states</b>: a fixed list, like locked and unlocked;
- its <b>inputs</b>: what can happen, like a coin or a push;
- its <b>transitions</b>: for every state and input, which state comes next;
- its <b>outputs</b>: what it shows or does in each state.

"Finite" means the list of states is fixed in advance. That's what makes it buildable: a fixed number of states fits in a fixed number of bits.

The transitions are usually drawn as circles joined by arrows. A table says the same thing and is easier to turn into gates:

## States as bits

To build a state machine, give every state a bit pattern. The turnstile has two states, so one bit is enough: U = 1 for unlocked, U = 0 for locked. A machine with 3 or 4 states needs 2 bits, one with 5 to 8 states needs 3, and so on: the same "each bit doubles the patterns" rule from the codebook.

Once the states are bits, the next-state table is a truth table: the current state bits and the inputs go in, the next state bits come out. And any truth table can be built from gates.

<KeyIdea>Encode the states in bits, and the next-state table becomes a truth table. The register holds the bits; gates compute the next ones.</KeyIdea>

## Build the turnstile

The turnstile has one state bit, U, and two inputs, COIN and PUSH (one at a time). Reading the table row by row:

- A coin always leads to unlocked.
- Without a coin, it ends up unlocked only if it was unlocked and nobody pushed.

The starting line below only listens to the coin, so it locks again as soon as nobody is paying, even if nobody has gone through. Fix it, then check the whole timeline matches.

<details>
<summary>Check your answer</summary>

`U := COIN OR (U AND NOT PUSH)`. The third tick is where the starting circuit first goes wrong: nothing happens, so the turnstile should stay unlocked, but `U := COIN` locks it. When a machine misbehaves, look for that first wrong tick; everything after it follows from it.

</details>

## A traffic light with two bits

A traffic light cycles green, yellow, red, green, and so on, one step per tick. Three states need two bits, S1 and S0:

<TruthTable caption='The traffic light, encoded' rowsJson='[["state", "S1", "S0", "next state"], ["green", "0", "0", "yellow (0 1)"], ["yellow", "0", "1", "red (1 0)"], ["red", "1", "0", "green (0 0)"]]' />

The pattern 1 1 is never used. From the table: S1 is 1 next only when the state now is yellow, so S1 := S0. S0 is 1 next only when the state now is green, so S0 := NOT S1 AND NOT S0.

The outputs are combinational: each light is a gate reading the state bits. GREEN is NOT S1 AND NOT S0, YELLOW is S0, and RED is S1.

The starting circuit below gets S1 right but S0 wrong: it goes back to yellow after red, skipping green. Fix S0.

<details>
<summary>Check your answer</summary>

`S0 := NOT S1 AND NOT S0`. The lights then go yellow, red, green, yellow, red, green. With `S0 := NOT S0`, red (1 0) went to 0 1, yellow again, because nothing stopped S0 from flipping on.

</details>

<KeyIdea>A state machine is a table of steps turned into a register and gates. Change the table, and you change what the machine does.</KeyIdea>
