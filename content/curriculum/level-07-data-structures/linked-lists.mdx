A dynamic array keeps its items side by side and moves them all when it grows. A **linked list** does the opposite: each item lives in its own small heap block, a **node**, and each node points to the next. Nothing ever moves, and inserting at the front never copies anything, but finding the 500th item means following 500 pointers.

## Nodes and links

```c
typedef struct Node {
    int value;
    struct Node *next;   /* the next node, or NULL at the end */
} Node;
```

The list itself is just a pointer to the first node, `Node *head`, and `NULL` means an empty list. Adding at the front makes a node, points it at the old head, and makes it the new head:

```c
static int push_front(Node **head, int value) {
    Node *n = malloc(sizeof *n);
    if (n == NULL) {
        return -1;           /* the list is unchanged */
    }
    n->value = value;
    n->next = *head;
    *head = n;
    return 0;
}
```

It takes `Node **` because it must change the caller's `head`. The list **owns** every node: one `list_free` call at the end frees them all, and nothing else frees a node that's still linked in.

Pushing at the front reverses the order: `50 -> 40 -> 30 -> 20 -> 10 -> NULL`. Finding 10 visits all 5 nodes, because it's at the end; finding 50 visits 1. Search is **O(n)**: there's no way to jump into the middle of a list. After removing 30 and 50: `40 -> 20 -> 10 -> NULL`.

`remove_value` walks with a **pointer to the link** (`Node **link`), the field that points at the current node. When it finds the value, it unlinks the node (`*link = dead->next`) and then frees it. Because `link` can be `&head` itself, removing the first node needs no special case.

</details>

| | Dynamic array | Linked list |
|---|---|---|
| Get item i | O(1) | O(n) |
| Add at the front | O(n) (shift everything) | O(1) |
| Add at the end | O(1) on average | O(n), or O(1) with a tail pointer |
| Remove a known node | O(n) (shift) | O(1) once you have its link |
| Memory per item | just the item | the item, a pointer and malloc's overhead |

On a real machine lists are often slower than the table suggests: their nodes are scattered around the heap, so walking one misses the cache at almost every step. The array's items sit side by side. Choose a list when you really insert and remove in the middle often, and hold on to the nodes.

## Freeing a list without reading freed memory

This `list_free` looks fine at a glance. It's built with AddressSanitizer: predict what happens.

<CRun program="data-structures/ll-free-bug" caption='A tidy-looking list_free' predict />

<details>
<summary>Check your answer</summary>

gcc warns at compile time, "pointer 'n' used after 'free'", and ASan stops the run with a **heap-use-after-free** in `list_free` at `main.c:20`. The loop frees `n`, then its step, `n = n->next`, reads `next` from the node it just freed. "freed it" is never printed.

The fix reads `next` before freeing, as the lesson's `list_free` does:

```c
while (head != NULL) {
    Node *next = head->next;   /* read it while the node still exists */
    free(head);
    head = next;
}
```

Without ASan this bug often seems to work, because freed memory usually keeps its old contents for a while. That's exactly why it's dangerous.

</details>

<KeyIdea>A linked list trades fast access by position for cheap inserts and removals. Its discipline: unlink before you free, and read next before you free.</KeyIdea>
