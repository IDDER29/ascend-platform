A mutex makes a whole critical section one-thread-at-a-time. For a single variable there's a lighter tool: an **atomic** operation, which the hardware performs as one indivisible step. C11 provides them in `<stdatomic.h>`. This lesson is a first, practical look; the full memory model is a deep subject of its own.

## An atomic counter

The racy counter again, this time with an `atomic_long` and `atomic_fetch_add`. That's read, add and write as one step, which on x86 is a single `lock`-prefixed instruction. It counts twice: once with the default ordering, and once with `memory_order_relaxed`. Predict both totals.

<CRun program="vm-threads-files/th-atomic-counter" caption='Two threads, atomic increments' predict />

<details>
<summary>Check your answer</summary>

Both are exactly 2000000, on every run. The increment is indivisible, so no update is lost, with no lock at all.

The two orderings differ in what *else* they promise. The default, `memory_order_seq_cst`, also keeps this access in order with the thread's other atomic accesses, and that order is the same for every thread. `memory_order_relaxed` promises only that the operation itself is atomic. For a counter that nothing else depends on, relaxed is enough, and it can be cheaper. Being sure you only need that much is the hard part, so start with the default.

</details>

## Compare and swap

Not everything is an addition. To update a shared maximum without a lock, read it, decide, and write only **if nobody changed it in between**. That is **compare-and-swap** (CAS):

```c
int seen = atomic_load(&best);
while (value > seen) {
    if (atomic_compare_exchange_weak(&best, &seen, value)) {
        return;                    /* best was still `seen`: now it's `value` */
    }
    /* someone else changed best: seen now holds its new value, so check again */
}
```

Four threads each feed 100000 numbers through this. Then main finds the maximum again with a plain loop to check.

<CRun program="vm-threads-files/th-atomic-cas" caption='A lock-free maximum' predict />

<details>
<summary>Check your answer</summary>

The two agree: 1000002. When CAS fails, it hands back the value it found, and the loop decides again with fresh information. If another thread already stored something larger, the `while` condition becomes false and this thread gives up, which is correct. The `_weak` version may also fail now and then for no reason (a spurious failure), which the loop absorbs. It's what to use inside a loop.

CAS is the building block of lock-free stacks, queues and reference counts. It's also easy to get wrong, so reach for a mutex unless you've measured that the lock is your bottleneck.

</details>

<KeyIdea>An atomic operation can't be torn or interleaved. atomic_fetch_add for counters, compare-and-swap in a loop for anything that depends on the old value.</KeyIdea>

## When order isn't program order

Here's something that looks impossible. Two threads, and two flags `x` and `y`, both starting at 0:

| Thread 1 | Thread 2 |
|---|---|
| `x = 1;` | `y = 1;` |
| `r1 = y;` | `r2 = x;` |

If each thread's two lines happened in order, at least one of them would run its store before the other's load, so `r1` and `r2` can't **both** be 0. This program runs the test 200000 times with relaxed atomics, then 200000 times with the default seq_cst, and counts how often both read 0. The counts change from run to run and from machine to machine.

<CRun program="vm-threads-files/th-reorder" caption='The store-buffering test' predict />

<details>
<summary>Check your answer</summary>

With relaxed atomics, both threads read 0 in about 39000 of 200000 trials on this run. With seq_cst, never.

Each x86 core puts its stores in a **store buffer** and lets later loads go ahead without waiting for them to reach memory. With relaxed ordering, gcc compiles each store to a plain `mov`. So thread 1's load of `y` ran while its `x = 1` was still in its own buffer, invisible to thread 2, and the same happened the other way round. With seq_cst, gcc compiles the store to `xchg`, which waits for the buffer to drain before the load can go: the "impossible" outcome disappears. Compilers may reorder independent accesses too, unless the orderings forbid it.

This is why ordinary variables shared between threads need a lock or atomics, even when "it's just a flag": without them, neither the compiler nor the CPU promises another thread sees your writes in the order you made them.

</details>
