You've built a CPU from gates, written its programs in assembly, and translated a small language into them. This course puts that CPU back where it lives: inside a whole computer.

By the end you'll be able to name each part of a computer system, say what job it does, and say which parts the tiny CPU leaves out.

## The CPU alone

A CPU fetches an instruction, does it, and fetches the next. That's all it does. On its own it has nowhere to fetch instructions from, nowhere to keep more than a few values, and no way to show anyone a result.

The tiny CPU already needed two more things to be useful: 256 bytes of **memory** holding its program and data, and **devices** reached through `IN` and `OUT`. Here it reads a number from an input device and shows it on the display. It should show one more than it reads.

## Six parts, six jobs

A real computer has more parts, and each has one clear job:

<TruthTable caption='The parts of a computer system' rowsJson='[["part", "its job", "keeps data with the power off?"], ["CPU", "runs instructions, one after another", "no"], ["memory (RAM)", "holds the running programs and their data", "no"], ["storage (SSD or disk)", "keeps programs and files for later", "yes"], ["firmware", "the first program to run at power-on", "yes, in a small chip"], ["devices", "keyboard, display, network, sound and more", "depends on the device"], ["operating system", "runs programs and shares the hardware between them", "kept in storage"]]' />

The parts talk through agreed **interfaces**: the CPU reads memory by address, sends bytes to a device through its controller, and asks storage for blocks of data. Because each part only has to keep its side of the interface, you can swap a bigger SSD or a faster memory stick into a PC and the rest keeps working.

<KeyIdea>A computer is a CPU plus memory, storage, firmware, devices and software, each with one job, connected by agreed interfaces.</KeyIdea>

## Following one keypress

Press a key in a text editor, and every part takes a turn:

1. The keyboard's controller notices the key and tells the CPU, as you saw in *Input and output*.
2. The operating system's keyboard code, running on the CPU, reads the key and hands it to the editor.
3. The editor, also running on the CPU, adds the letter to the text it keeps in memory.
4. The operating system and the display controller draw the new letter on the screen.
5. Nothing reaches storage until you save. Then the file's bytes go to the SSD, where they stay with the power off.

The rest of this course takes those parts one at a time: memory and storage, the hierarchy of faster and slower memory, startup, and then the operating system.

## The toy and the real thing

The tiny CPU is honest about its own machine, but it leaves a lot out:

- Its memory is 256 bytes and starts already loaded with the program. Real memory starts empty, and something has to load the program in.
- It has no storage, so nothing it does survives.
- It has no firmware and no operating system: one program owns the whole machine.
- Its devices are just numbered ports for `IN` and `OUT`.

None of that makes it wrong. It makes it small. Each lesson from here adds back one of those missing pieces and shows what it's for.
