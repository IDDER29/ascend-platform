The tiny CPU from Foundations did one instruction completely before starting the next: fetch it, decode it, execute it, then fetch the next. A **pipeline** overlaps that work. While one instruction executes, the next is being decoded and the one after that fetched, like an assembly line where each station works on a different car.

## A small instruction set

This course uses a small part of **RISC-V**, a real, open instruction set:

- 32 registers, `x0` to `x31`. `x0` always reads 0, and writing to it does nothing.
- `add x3, x1, x2` sets x3 = x1 + x2. `sub`, `and`, `or` and `slt` (set if less than) work the same way.
- `addi x1, x0, 5` adds a constant: here x1 = 0 + 5.
- `lw x2, 8(x1)` loads the 4-byte word at address x1 + 8 into x2; `sw x2, 8(x1)` stores x2 there.
- `beq x1, x2, done` jumps to the label `done` if x1 equals x2; `bne` jumps if they differ.

The destination comes first, then the sources: the opposite of the AT&T syntax gcc prints for x86-64.

## The five stages

Each instruction goes through five stages, one per clock cycle:

| Stage | Name | What happens |
|---|---|---|
| IF | Instruction fetch | Read the instruction at PC from instruction memory; PC moves on by 4 |
| ID | Instruction decode | Work out what it is, and read its source registers |
| EX | Execute | The ALU computes: the sum, the address for a load or store, or the branch comparison |
| MEM | Memory | A load reads data memory, a store writes it; other instructions pass through |
| WB | Write back | The result is written into the destination register |

Between stages sit **pipeline registers** that hold each instruction's values as it moves on, so every stage can work on a different instruction in the same cycle.

## Watch it fill

Five independent instructions: none uses a result of another. Each row is an instruction; each column is a clock cycle.

In cycle 5 all five stages are busy at once: the first instruction is in WB and the fifth is in IF. How many cycles would 8 such instructions take? And 1000?

<details>
<summary>Check your answer</summary>

The first instruction takes 5 cycles to get through. After that, one instruction finishes every cycle. So:

- 5 instructions take 5 + 4 = **9** cycles, as the lab shows.
- 8 take 8 + 4 = **12**.
- 1000 take 1000 + 4 = **1004**.

The 4 extra cycles are the time to fill the pipeline. Cycles per instruction (**CPI**) is 9 / 5 = 1.8 for the short program, but 1004 / 1000 is about 1.004 for the long one: an ideal pipeline approaches a CPI of 1.

</details>

<KeyIdea>A pipeline starts a new instruction every cycle and finishes one every cycle once it's full: n independent instructions take n + 4 cycles in five stages.</KeyIdea>

## Faster, but not quicker

Suppose, as an illustration, the stages take 200, 100, 200, 200 and 100 picoseconds. A single-cycle CPU does all five in one long cycle of 800 ps. A pipelined one needs a clock slow enough for its **slowest** stage, 200 ps, since every stage must finish within one cycle.

For 1000 instructions, which is faster, and how long does one instruction take in each?

<details>
<summary>Check your answer</summary>

- Single cycle: 1000 × 800 ps = **800 ns**.
- Pipelined: (1000 + 4) × 200 ps = **200.8 ns**, almost 4 times faster.

But one instruction takes 5 × 200 = **1000 ps** in the pipeline, longer than the 800 ps of the single-cycle design. The pipeline doesn't make an instruction quicker; it makes more of them finish per second. That's **throughput** versus **latency**.

It isn't 5 times faster, because the stages aren't equal: the 100 ps stages waste half of each cycle. Real pipelines also lose a little time in the pipeline registers between stages. That's why designers work hard to balance the stages.

</details>

## The catch

The diagram above is the ideal case. Real programs have instructions that depend on each other, and branches whose direction isn't known until EX. Look at the lab's numbers: **stalls**, **branch bubbles** and **flushed** are all 0 here. The next three lessons are about what makes them grow, and what hardware does about it.
