`printf` doesn't print. It copies bytes into a **buffer** in your own process's memory; only when the buffer is flushed does stdio call `write`, the system call that hands bytes to the kernel. Since a system call costs far more than copying a few bytes, stdio sends as few as it can. This lesson shows when that happens, and the surprises that come with it.

## Where the bytes wait

stdio sets each output stream's mode when the program starts:

| stdout goes to | Mode | Flushed when |
|---|---|---|
| a terminal | **line buffered** | a newline is written, or the buffer fills |
| a pipe or a file | **fully buffered** | the buffer (4096 bytes here) fills |
| (stderr, anywhere) | **unbuffered** | every call |

Every stream is also flushed by `fflush`, by `exit` (and returning from `main`), and before stdio reads from a line-buffered input. Here is a program that `printf`s 1000 lines, `line 1` to `line 1000`, 8893 bytes in all, traced with `strace -e trace=write` on real Linux runs (the terminal is provided by `script`). The counts and sizes are summarised from strace's log; the `write` lines are copied from it:

```
to a terminal: 1000 write calls
write(1, "line 1\n", 7)                 = 7
write(1, "line 2\n", 7)                 = 7
to a pipe: 3 write calls
write(1, "line 1\nline 2\nline 3\nline 4\nline"..., 4096) = 4096
to a file: 3 write calls
sizes: 4096 4096 701
```

Same program, same output, 333 times fewer system calls when nobody is watching line by line. That's why buffering exists.

<details>
<summary>Check your answer</summary>

1. `B A C`. `"A "` and `"C\n"` went into the buffer; `write` sent `"B "` straight to the kernel. The buffer was flushed at exit, after B. On a terminal you'd still see `B A C`, because `"A "` has no newline; the order only looks right when every `printf` ends a line.
2. The line appears **twice**. `printf` left it in the buffer, `fork` copied the whole process memory including the buffer, and both parent and child flushed their copy when they exited. On a terminal it would appear once: the newline had already sent it before `fork`.
3. **Nothing** is printed. Both lines were waiting in the buffer when the null-pointer write killed the process with `SIGSEGV`, and a process killed by a signal never runs `exit`, so the buffer was never flushed. The output was lost. That's how a log "stops" a few lines before the real crash.

</details>

<KeyIdea>printf writes into memory in your process; only a flush calls write and reaches the kernel. Whatever is still in the buffer when you fork is copied, and whatever is there when you crash is lost.</KeyIdea>

## Fixes

Each surprise has a standard fix:

- **Before `fork` or `exec`, call `fflush(stdout)`** (or `fflush(NULL)` for every stream), so nothing is copied or thrown away. Shells and servers do this everywhere.
- **For progress messages and logs, choose line buffering** with `setvbuf(stdout, NULL, _IOLBF, 0)` at the start, or write diagnostics to **stderr**, which is unbuffered.
- **Don't mix** `printf` and `write` on the same descriptor; if you must, `fflush` first.
