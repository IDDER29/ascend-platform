A storage device knows nothing about files. An SSD stores numbered blocks of bytes, and that's all. "notes.txt in your Documents folder" is something the operating system builds on top of those blocks, and every program reaches it through the OS.

By the end you'll be able to follow a save from a program to the disk, and say exactly when the data is safe.

## A file is a name for bytes

To a program, a file is:

- a **name** (notes.txt) in a **folder**,
- a sequence of **bytes** (here, three: `o`, `k` and a newline),
- some **details**: its size, who may read or write it, when it changed.

The file system's job is to keep that picture true on a device that only has numbered blocks: which blocks hold this file's bytes, where its details are, which blocks are free.

## Saving goes through the OS

This C program saves "ok" to notes.txt:

```c
#include <stdio.h>

int main(void) {
    FILE *f = fopen("notes.txt", "w");
    if (f == NULL) return 1;
    fprintf(f, "ok\n");
    fclose(f);
    return 0;
}
```

`strace` lists the system calls a program makes. Here are the ones for notes.txt (gcc 15.2 on Linux; other systems show different details):

```
openat(AT_FDCWD, "notes.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
write(3, "ok\n", 3)                     = 3
close(3)                                = 0
```

- `openat` asks the kernel to open (and create, and empty) notes.txt. The kernel returns **3**, a file descriptor: this process's number for the open file.
- `write(3, ...)` hands the kernel three bytes for file 3. It returns 3: three bytes accepted.
- `close(3)` says the program is done with file 3.

The program never touched the SSD. It only asked, and the kernel did the rest.

## Saving is not the same as changing RAM

When `write` returns, where are the bytes? On Linux, usually in the kernel's **page cache**, in RAM. The kernel writes them to the disk a little later, often within seconds, because collecting many writes and sending them together is much faster. Until then, a power cut loses them.

The lab below is a teaching model of this. In the model, a file write goes into the kernel's RAM cache, and the cache is written to the disk on `close`, `sync` or `exit`. That's a simplification: real Linux does not write to the disk on close. It writes back on its own schedule, and only `fsync` (for one file) or `sync` (for everything) forces it.

## Where the bytes really go

`stat` shows what the file system keeps for notes.txt:

```
name notes.txt, size 3 bytes, 8 blocks of 512 bytes, inode 104185
```

- **size 3 bytes**: the file's length, as the program sees it.
- **8 blocks of 512 bytes**: the file system gave it 4096 bytes of storage, because it hands out space in 4096-byte chunks. A 3-byte file still takes a whole chunk.
- **inode 104185**: the number of the file's record, which holds its size, owner, permissions, times and where its blocks are.

## Folders map names to files

The name "notes.txt" isn't stored in the inode. It's stored in the folder. A folder is a small table:

Opening a file means finding its name in the folder's table, following the inode number to its record, and from there finding its blocks. Renaming a file only changes the folder's table; the bytes don't move.

<details>
<summary>Check your answer: you move a 2 GB video into another folder on the same disk, and it finishes instantly. Why?</summary>

Moving within one file system only removes the name from one folder's table and adds it to another's, pointing at the same inode. None of the 2 GB of blocks is copied. Moving to another disk is slow because there the bytes really have to be copied.

</details>
