Coherence answers "which value of `x` is current?". It says nothing about this: if one core writes `x` and then `y`, can another core see the new `y` but the old `x`? That's the **memory consistency model**: the rules for the order in which one core's memory operations to *different* addresses become visible to the others.

## The model you'd expect

**Sequential consistency** (SC), defined by Leslie Lamport in 1979, is the intuitive one: the result is as if all cores' operations were interleaved into one sequence, each core's operations staying in program order. Any interleaving is allowed; reordering within a core is not.

SC is easy to reason about, and no mainstream CPU provides it by default, because keeping every load and store in order costs too much. A core would have to wait for each store to reach the cache before doing anything else. Instead, each architecture defines a weaker model and gives you **fences** to get order back where you need it.

## Three litmus tests on this machine

A **litmus test** is a tiny two-thread program with one outcome that some models allow and others forbid. Run it many times and see if the outcome ever happens. This program runs three tests, 100000 times each, using relaxed atomics so the compiler emits plain loads and stores, with compiler-only barriers so gcc can't reorder them either. What you see is the hardware's ordering.

- **Store buffering:** thread 1 does `x = 1; r1 = y`, thread 2 does `y = 1; r2 = x`. Can both read 0?
- **The same with a full fence** between each store and load.
- **Message passing:** thread 1 does `x = 1; y = 1` (data, then flag); thread 2 does `r1 = y; r2 = x`. Can the flag be 1 but the data 0?

Under SC, none of these outcomes is possible. Predict which ones x86 shows.

- **Store buffering, no fence:** both loads read 0 in tens of thousands of trials (the exact count changes every run). x86 lets a later load go ahead of an earlier store to a different address.
- **With the fence:** never.
- **Message passing:** never, in 100000 trials. In a separate check, the reader saw the flag set in about 45% of trials, and every time it also saw the data. x86 keeps stores in order with other stores, and loads in order with other loads.

So x86 relaxes exactly one of SC's four orderings: **a store followed by a load** (to a different address) can appear reordered. That model is **TSO**, total store order.

</details>

## The store buffer

Why that one reordering? Each core has a **store buffer**: a small queue of stores that have executed but not yet been written into the L1 cache. A store waiting for its cache line (perhaps another core holds it in M) sits there while the core carries on. Later loads don't wait for it: they read the cache, or take their value from the buffer if it holds a store to the same address.

In the store-buffering test, both cores park their `= 1` in their own buffers and immediately load the other variable from the cache, where it's still 0. Coherence is not broken: it covers values in the caches, and the stores hadn't got there yet. Because the buffer drains in order (first in, first out), stores still become visible in program order, which is why message passing works on x86.

A **full fence** makes the core wait until its store buffer is empty before any later load. In the program, `atomic_thread_fence(memory_order_seq_cst)` is what gcc 15 compiled into the fence. The real `-O2` output contains no `mfence`, but this:

```
lock orq	$0, (%rsp)
```

A locked instruction drains the store buffer just as `mfence` does, and is often cheaper, so gcc uses it on a harmless stack address. The `atomic_store` with the default `seq_cst` order from the atomics lesson compiled to `xchg`, which is locked too, for the same reason.

<KeyIdea>Coherence orders writes to one address; the consistency model orders accesses to different addresses. On x86, the store buffer lets a later load overtake an earlier store, and a fence (a locked instruction) drains the buffer to stop it.</KeyIdea>

## Weaker than TSO

ARM, POWER and RISC-V (with its default RVWMO model) are weaker. They allow stores to different addresses to become visible out of order, and loads to complete out of order. On those machines the message-passing test **can** fail without help: the reader can see the flag and still read the old data.

Portable C states the order it needs and lets the compiler pick instructions:

```c
/* writer */
data = 42;
atomic_store_explicit(&ready, 1, memory_order_release);

/* reader */
while (!atomic_load_explicit(&ready, memory_order_acquire)) {
}
use(data); /* guaranteed to see 42 */
```

A **release** store makes all earlier writes visible before it; an **acquire** load keeps all later reads after it. On ARMv8 these become `stlr` and `ldar`, instructions with ordering built in. On x86 they become ordinary `mov`s, because TSO already gives these orderings for free.

Try it: which of these would you need on x86, and which on ARM, for the message-passing pattern to be correct?

1. A full fence between the writer's two stores.
2. Release on the flag store and acquire on the flag load.
3. Nothing at all.

<details>
<summary>Check your answer</summary>

On x86, 3 happens to work in the hardware, as the litmus test showed. But in C you still need 2, because the *compiler* may reorder plain or relaxed accesses; release and acquire cost nothing extra on x86. On ARM, 2 is needed, and enough: the release keeps `data` before `ready`, and the acquire keeps the read of `data` after it. A full fence (1) on the writer's side alone would also order the stores, but it does nothing for the reader's loads, and it's stronger and slower than needed. Write 2 everywhere, and the code is correct on every architecture.

</details>
