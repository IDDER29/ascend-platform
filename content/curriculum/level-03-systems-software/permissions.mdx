Every process runs as a **user** (a number, the uid) and belongs to some **groups** (gids). Every file has an owner, a group and a set of permission bits. When a process calls `open`, `execve`, `mkdir` or any other system call that touches a file, the kernel compares the two and says yes or no. This lesson is about that comparison.

The sessions below are real, run in `/tmp` on Linux. The account name has been replaced with `learner`.

## Reading a permission string

```
$ ls -l notes.txt
-rw-rw-r-- 1 learner learner 12 Oct 31 13:07 notes.txt
$ chmod 600 notes.txt; ls -l notes.txt
-rw------- 1 learner learner 12 Oct 31 13:07 notes.txt
$ chmod u=rw,g=r,o= notes.txt; ls -l notes.txt
-rw-r----- 1 learner learner 12 Oct 31 13:07 notes.txt
```

The first character is the type (`-` for a file, `d` for a directory). Then come three groups of three: the **owner's**, the **group's** and **everyone else's**, each `r`ead, `w`rite and e`x`ecute. Each group is also one octal digit, with r = 4, w = 2, x = 1: `rw-` is 6, `r--` is 4, `---` is 0, so `-rw-r-----` is `0640`.

The kernel uses exactly **one** of the three groups: the owner's if the process's uid owns the file; otherwise the group's if the process is in the file's group; otherwise everyone else's. (The superuser, uid 0, skips most of these checks.)

## Directories are different

On a directory the bits mean something else:

- **r:** list the names in it.
- **w:** create, delete and rename entries in it (with x).
- **x:** pass through it, to reach a name you already know.

```
$ chmod 300 box; ls -ld box
d-wx------ 2 learner learner 60 Oct 31 13:08 box
$ ls box
ls: cannot open directory 'box': Permission denied
$ cat box/item.txt
inside
```

Why can you read a file in a directory you can't list? And what would happen with `r` but no `x`?

<details>
<summary>Check your answer</summary>

Opening `box/item.txt` only needs to *pass through* `box` to the name `item.txt`, which `x` allows. Listing needs `r`, which is missing. With `r` but no `x` you get the opposite: `ls box` shows the names, but opening any of them fails, because you can't pass through. This is also why deleting a file depends on the **directory's** `w` permission, not the file's: deleting changes the directory's list of names.

</details>

## Running programs and scripts

```
$ ls -l hello.sh
-rw-rw-r-- 1 learner learner 35 Oct 31 13:07 hello.sh
$ ./hello.sh
bash: ./hello.sh: Permission denied
$ chmod +x hello.sh; ./hello.sh
hello from a script
```

`execve` needs the `x` bit. Without it the shell reports `Permission denied`, and exit status 126.

## The mode a new file gets

A program passes a mode to `open` or `mkdir`, usually 0666 for files and 0777 for directories, and the kernel clears the bits in the process's **umask**. A umask of 022 removes write permission for group and others (0666 becomes 0644). Many desktop Linux systems use 002, which keeps write permission for your own group (0664, `-rw-rw-r--`, as in the first `ls -l` above). The umask is inherited across `fork` and `exec`, like the environment.

## Raising privileges on purpose: setuid

```
$ ls -l /etc/shadow /usr/bin/passwd
-rw-r----- 1 root shadow  1326 Aug 19 00:26 /etc/shadow
-rwsr-xr-x 1 root root   93640 Feb  2  2026 /usr/bin/passwd
```

Ordinary users can't read `/etc/shadow`, yet `passwd` changes your password inside it. How?

<details>
<summary>Check your answer</summary>

The `s` in `-rwsr-xr-x` is the **setuid** bit. When anyone runs `passwd`, `execve` gives the new process the file owner's user id, root, as its *effective* uid, so the kernel's checks treat it as root. `passwd` is written carefully to change only the calling user's own entry. A setuid-root program with a bug lets any user act as root, which is why there are very few of them and why they are audited closely.

</details>

<KeyIdea>Every process has a user and groups; every file has an owner, a group and nine permission bits. The kernel compares them on each system call that opens, runs or changes a file, using only the owner's, the group's or everyone else's bits.</KeyIdea>
