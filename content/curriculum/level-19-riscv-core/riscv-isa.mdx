In Pipelining you ran a small subset of RISC-V through a five-stage pipeline. Now meet the whole base instruction set, **RV32I**: 32-bit registers, 32-bit instructions, and only about forty instructions. That's the processor you'll build in the capstone. In this lesson you'll learn to read it the way the hardware does, bit by bit.

The machine code below is real: C compiled with gcc 14.2 for `-march=rv32i -mabi=ilp32 -O2`, then disassembled with `riscv64-unknown-elf-objdump -d`.

## Registers and their ABI names

RV32I has 32 registers, `x0` to `x31`, each 32 bits wide, plus the program counter. Hardware treats them all alike except one: **`x0` always reads 0**, and writes to it are thrown away. The calling convention (the ABI) gives the others names that say how software uses them:

| Register | ABI name | Used for |
|---|---|---|
| x0 | zero | always 0 |
| x1 | ra | return address |
| x2 | sp | stack pointer |
| x5 to x7, x28 to x31 | t0 to t6 | temporaries (the caller saves them if it needs them) |
| x8 to x9, x18 to x27 | s0 to s11 | saved (the callee must restore them) |
| x10 to x17 | a0 to a7 | arguments; a0 and a1 also return values |

So in `add a0,a0,a1`, a0 is x10 and a1 is x11. Disassemblers print ABI names, but the machine code only ever holds the numbers.

## Six formats, fixed fields

Every instruction is 32 bits. The low 7 bits, the **opcode**, say which format the rest follows:

| Format | Used by | bits 31 to 25 | 24 to 20 | 19 to 15 | 14 to 12 | 11 to 7 | 6 to 0 |
|---|---|---|---|---|---|---|---|
| **R** | register-register (add, sub, and, slt) | funct7 | rs2 | rs1 | funct3 | rd | opcode |
| **I** | immediates and loads (addi, lw, jalr) | imm[11:5] | imm[4:0] | rs1 | funct3 | rd | opcode |
| **S** | stores (sw) | imm[11:5] | rs2 | rs1 | funct3 | imm[4:0] | opcode |
| **B** | branches (beq, bne, blt) | imm[12\|10:5] | rs2 | rs1 | funct3 | imm[4:1\|11] | opcode |
| **U** | upper immediates (lui, auipc) | imm[31:12] across bits 31 to 12 | | | | rd | opcode |
| **J** | jal | imm[20\|10:1\|11\|19:12] across bits 31 to 12 | | | | rd | opcode |

Look down the columns: wherever a format has `rs1`, `rs2` or `rd`, it's in the same place. That's deliberate, and it's the key to everything below.

## Decoding an R-type word

The function `add3(a, b, c)` compiled to:

```
00000000 <add3>:
   0:	00b50533          	add	a0,a0,a1
   4:	00c50533          	add	a0,a0,a2
   8:	00008067          	ret
```

Here is `0x00b50533` split into the R-type fields:

| funct7 | rs2 | rs1 | funct3 | rd | opcode |
|---|---|---|---|---|---|
| 0000000 | 01011 | 01010 | 000 | 01010 | 0110011 |
| 0 | 11 (a1) | 10 (a0) | 0 | 10 (a0) | R-type ALU |

Opcode `0110011` means "register-register ALU", and funct3 `000` with funct7 `0000000` means **add**: x10 = x10 + x11. `ret` is not an instruction of its own; it's the pseudo-instruction for `jalr x0, 0(ra)`, jump to the return address and throw the link away.

Predict: plain RV32I has no multiply instruction. What does gcc do with `return x * x;`?

```
   0:	02a50533          	mul	a0,a0,a0

```

Compare `mul` (`0x02a50533`) with `add`: same opcode, same funct3, only funct7 changes from `0000000` to `0000001`. Extensions fit into the same formats. RISC-V is a small base plus optional extensions (M, A, F, D, C and more), and a chip implements the ones it needs.

</details>

## Loads, stores and the split immediate

`copy_next(p)` does `p[1] = p[0] + 5;`:

```
0000000c <copy_next>:
   c:	00052783          	lw	a5,0(a0)
  10:	00578793          	addi	a5,a5,5
  14:	00f52223          	sw	a5,4(a0)
  18:	00008067          	ret
```

A load is I-type: `lw a5,0(a0)` reads the word at a0 + 0 into a5. A store has no destination register, so S-type uses those 5 bits for part of the offset instead. `0x00f52223`:

| imm[11:5] | rs2 | rs1 | funct3 | imm[4:0] | opcode |
|---|---|---|---|---|---|
| 0000000 | 01111 | 01010 | 010 | 00100 | 0100011 |
| | 15 (a5) | 10 (a0) | word | | store |

The offset is `0000000` joined to `00100`: 4. So it stores a5 at a0 + 4, which is `p[1]`. The value comes from rs2, and rs1 is the base, in the same places as in `add`.

## Branches and jumps

The loop in `sum(a, n)`:

```
00000030 <.L6>:
  30:	0007a703          	lw	a4,0(a5)
  34:	00478793          	addi	a5,a5,4
  38:	00e50533          	add	a0,a0,a4
  3c:	fed79ae3          	bne	a5,a3,30 <.L6>
```

`bne` at address 0x3c jumps back to 0x30. Decode `0xfed79ae3` and find the offset.

<details>
<summary>Check your answer</summary>

| imm[12] | imm[10:5] | rs2 | rs1 | funct3 | imm[4:1] | imm[11] | opcode |
|---|---|---|---|---|---|---|---|
| 1 | 111111 | 01101 | 01111 | 001 | 1010 | 1 | 1100011 |
| | | 13 (a3) | 15 (a5) | bne | | | branch |

Put the immediate bits back in order: imm[12] = 1, imm[11] = 1, imm[10:5] = 111111, imm[4:1] = 1010, and imm[0] is always 0 (branch targets are at least 2-byte aligned). That's `1111111110100` in 13 bits. With bit 12 as the sign it's **-12**, and 0x3c - 12 = 0x30, the top of the loop.

</details>

A branch's offset counts in multiples of 2 bytes, so 12 bits of immediate reach ±4 KiB. **`jal`** (J-type) has 20 bits for ±1 MiB, and writes the return address into rd. In the linked program, `start` calls `square` with:

```
   100bc:	fd9ff0ef          	jal	10094 <square>
```

Its rd field is `00001`, ra, and its immediate decodes to -40: 0x100bc - 40 = 0x10094. **`jalr`** (I-type) jumps to a register plus an offset, which is how `ret` and calls through function pointers work.

## Big constants: LUI and AUIPC

An I-type immediate holds only 12 bits. To build any 32-bit constant, RISC-V uses two instructions. **`lui rd, imm`** puts a 20-bit immediate into the top 20 bits of rd, then `addi` adds the low 12:

```
0000004c <big>:
  4c:	12345537          	lui	a0,0x12345
  50:	67850513          	addi	a0,a0,1656 # 12345678
```

0x12345000 + 0x678 (1656) = 0x12345678. But here's a function returning **0x12345878**:

```
00000000 <big2>:
   0:	12346537          	lui	a0,0x12346
   4:	87850513          	addi	a0,a0,-1928 # 12345878
```

Why 0x12346, not 0x12345?

<details>
<summary>Check your answer</summary>

ADDI's immediate is **sign-extended**: the 12 bits 0x878 have their top bit set, so as an immediate they mean -1928, not +2168. If LUI loaded 0x12345000, the sum would come out 0x800 too small. So the compiler adds one to the upper part: 0x12346000 - 1928 = 0x12345878. **`auipc`** works like `lui` but adds the upper immediate to the PC, which is how code reaches addresses relative to where it is running.

</details>

## Why it's designed this way

- **Fixed fields.** `rs1`, `rs2` and `rd` never move, so the hardware can start reading the register file while it is still decoding the opcode. In a pipeline that's time saved in every instruction.
- **The sign bit is always bit 31.** Every immediate can be sign-extended before the decoder knows which format it is.
- **Scrambled immediates.** The odd bit order of B and J immediates keeps as many immediate bits as possible in the same positions across formats, so the hardware that gathers them is just a few multiplexers. It's harder for people to read, easier for hardware.
- **`x0` is zero.** Many operations come free: `mv` is `addi rd, rs, 0`, `li` is `addi rd, x0, imm`, `nop` is `addi x0, x0, 0`, and a jump that throws away its return address writes to x0.
- **A small base.** RV32I has about forty instructions; multiply, atomics, floating point and compressed 16-bit instructions are optional extensions. A tiny core and a server chip share the same base.

<KeyIdea>Every RV32I instruction is 32 bits with the opcode in the low 7 and the registers always in the same places. Learn the six formats and you can decode any instruction by hand, and later in Verilog.</KeyIdea>
