A thread pool starts a few worker threads once, then feeds them tasks from a queue. In this project you read a complete pool, run its tests under ThreadSanitizer, and then meet the two classic ways such code goes wrong: a race and a lost wakeup.

## Part 1: The interface

```c
/* A fixed set of worker threads that run submitted tasks. The pool owns its
   threads and its queue; the caller owns each task's argument and must keep it
   alive until tp_wait has returned. */
typedef struct threadpool threadpool;

threadpool *tp_new(int workers);                          /* NULL on failure */
int tp_submit(threadpool *p, void (*fn)(void *), void *arg); /* 0 on success */
void tp_wait(threadpool *p);       /* returns when every submitted task has finished */
void tp_free(threadpool *p);       /* waits, stops the workers and frees the pool */
```

A task is a function pointer and a `void *` argument. What does the comment ask of the caller, and what could go wrong if the caller ignored it?

<details>
<summary>Check your answer</summary>

Each argument must stay alive until `tp_wait` returns, because a worker may run the task long after `tp_submit` has returned. If a caller passed the address of a local variable in a loop and then returned, or reused one variable for every task, the workers would read memory that had changed or no longer existed. The test below gives each task its own `job` in a static array, which lives for the whole program.

</details>

## Part 2: Read the pool

The run below prints all three files. In `threadpool.c`, the mutex `lock` guards everything in the struct after it, and there are two condition variables:

- **`has_work`:** a worker sleeps on it when the queue is empty; `tp_submit` signals it, and `tp_free` broadcasts it to wake every worker for shutdown.
- **`all_done`:** `tp_wait` sleeps on it until `pending`, the number of tasks queued or running, reaches 0. A worker broadcasts it when it finishes the last one.

Find two places where the code is careful about the lock, and say what each prevents.

<details>
<summary>Check your answer</summary>

- **The worker waits in `while (p->head == NULL && !p->stopping)`, not `if`.** `pthread_cond_wait` can return without a signal (a spurious wakeup), and even after a real signal another worker may already have taken the task. The loop re-checks the condition with the lock held, so a worker never takes from an empty queue.
- **The worker unlocks before `t->fn(t->arg)` and locks again after.** Tasks run in parallel, and the lock covers only the queue and the counters. Holding it while a task runs would make the pool run one task at a time.

Also notice:

- `tp_wait` checks `pending` in a `while` loop under the same lock that workers hold when they change it, so it can't miss the moment it reaches 0.
- `tp_free` sets `stopping` and broadcasts, and each worker leaves only once the queue is empty. Every submitted task still runs.

</details>

## Part 3: Run the tests

The test submits 1000 tasks, each squaring a number into its own `job`, then checks the total against the formula n(n + 1)(2n + 1) / 6. It then submits a second batch and frees the pool without calling `tp_wait`. It's built with **ThreadSanitizer** (`-fsanitize=thread`), which watches every memory access while the program runs and reports any two threads touching the same memory without synchronisation.

## Part 4: A race the tests miss

This version makes one change in the worker: it decrements `pending` before taking the lock again.

```c
free(t);
int left = --p->pending; /* the lock isn't held here */
pthread_mutex_lock(&p->lock);
if (left == 0) {
    pthread_cond_broadcast(&p->all_done);
}
```

Predict: do the tests still pass? Does ThreadSanitizer say anything?

<CRun program="vm-threads-files/pool-race" caption='The race, under ThreadSanitizer' show="main.c" predict />

<details>
<summary>Check your answer</summary>

The tests pass, and ThreadSanitizer reports a **data race** anyway. A worker writes `pending` at `threadpool.c:43` with no mutex held, while the main thread writes it in `tp_submit` at line 92 with the mutex held. TSan exits with status 66 to make the failure visible. (The addresses and thread ids in its report differ on every run.)

Both are right about what happened, but only TSan is right about the program. `--p->pending` is a read, a subtract and a write. If a worker and `tp_submit` interleave there, one update is lost:

- `pending` ends one too high: `tp_wait` sleeps forever.
- `pending` ends one too low: `tp_wait` returns while a task is still running, and the caller reads a result that isn't written yet.

This run's timing didn't lose an update. Another run, another machine or a busier system might. That's why concurrent code is checked with a race detector, not only with tests.

</details>

## Part 5: A wakeup that never comes

This version decrements `pending` correctly, under the lock, but forgets to broadcast `all_done` when it reaches 0. It's built without a sanitizer. Predict what it prints.

<CRun program="vm-threads-files/pool-hang" caption='The missing broadcast' show="main.c" predict />

<details>
<summary>Check your answer</summary>

It prints nothing and never finishes; the run was stopped after 3 seconds. Every task ran and `pending` reached 0, but `tp_wait` was asleep on `all_done`, and nothing ever signalled it. A condition variable has no memory: a thread that waits isn't woken by a change that happened without a signal.

Nothing printed because the first `printf` comes after `tp_wait`. There's no crash, no error and no sanitizer report, just a program that stops making progress. When you debug a hang, check every wait: what condition is it waiting for, and which code signals it when that condition becomes true? In gdb, `thread apply all bt` shows the main thread parked inside `pthread_cond_wait` from `tp_wait`.

</details>

<KeyIdea>A mutex protects shared state; a condition variable carries the news that the state changed. Wait in a loop, signal on every change someone may be waiting for, never touch shared state without the lock, and check it all with ThreadSanitizer.</KeyIdea>
