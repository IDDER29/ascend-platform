You'll often want to put a value aside for a moment and get it back later. A <b>stack</b> is the simplest way: you can only add to the top, and only take from the top, like a pile of plates. The last value in is the first one out.

By the end you'll be able to trace PUSH and POP on the tiny CPU, say where the stack lives, and say what happens when it fills up or runs dry.

## PUSH and POP

The tiny CPU keeps the top of the stack in a register called <b>SP</b>, the stack pointer. At the start SP is 0xF0, just above the stack area.

- <b>PUSH Rd</b> first takes 1 off SP, then stores Rd at the box SP points to.
- <b>POP Rd</b> first loads the box SP points to into Rd, then adds 1 to SP.

R2 gets 2 and R3 gets 1: the values come back in the opposite order. And notice that POP doesn't wipe the box. It only moves SP; the old value is still there until something overwrites it.

<KeyIdea>Last in, first out. PUSH: SP down, then write. POP: read, then SP up.</KeyIdea>

## The stack is ordinary memory

There is no stack chip. The stack is the ordinary RAM boxes 0xC0 to 0xEF, 48 bytes, that everyone agrees to use this way. PUSH, POP, CALL and RET follow the agreement; a plain STA R0, [0xEE] could still write in the middle of the stack, and nothing would stop it. Keeping out of the stack's way is the programmer's job.

## When the stack runs out

The stack has room for 48 bytes. This loop pushes forever:

<TinyCpu2 caption='Push until it is full' programJson='["loop: PUSH R0", "JMP loop"]' />

After 48 pushes SP is 0xC0, the bottom of the stack. The 49th push would write outside the stack area, so the CPU stops with <b>STACK_OVERFLOW</b> and changes nothing. Popping an empty stack (SP = 0xF0) stops with <b>STACK_UNDERFLOW</b> in the same way. Real computers have the same problem; a program that recurses forever ends with a "stack overflow" error.
