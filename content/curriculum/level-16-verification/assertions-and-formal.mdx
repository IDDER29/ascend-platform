Testbenches and coverage check the cases you run. This lesson is about stating what must *always* be true, then having a tool check it for every case at once.

## Assertions say what must be true

An **assertion** states a rule that should always hold, inside the design or the testbench. A saturating adder has an obvious one: adding never makes the result smaller than either input. In SystemVerilog:

```verilog
assert (y >= a && y >= b) else $error("y = %0d is smaller than an input", y);
```

If the condition is false when the line runs, the simulator reports an error with the time and place. Here it is in a testbench for the buggy adder from the Testbenches lesson, which only tries two input pairs:

<details>
<summary>Check your answer</summary>

3 + 4 passes. 9 + 9 fails: the assertion fires with `y = 2 is smaller than an input (a = 9, b = 9)`, at time 2 in scope `tb`. 9 + 9 = 18 wraps to 2 in the 4-bit sum. The simulation carries on and finishes, because `$error` reports without stopping.

An assertion only fires for the inputs that reach it, so a simulation still needs the right inputs. Formal tools remove that limit.

</details>

## A proof for every input

**Formal verification** doesn't run inputs. It turns the design and its assertions into a logic formula and asks a solver whether *any* input makes an assertion false. Here, Yosys converts the circuit and the assertions into a Boolean satisfiability (SAT) problem, and a SAT solver searches all 256 input pairs at once by reasoning, not by trying them.

This is the fixed adder, with two assertions written inside the design: never smaller than an input, and exactly the saturated sum.

<HdlRun design="verification/formal-good" caption='Proving the fixed adder' predict />

<details>
<summary>Check your answer</summary>

`SAT proof finished - no model found: SUCCESS!` The solver looked for an input, a **model**, that violates an assertion, and found none: both rules hold for every one of the 256 input pairs. The problem had 234 variables and 640 clauses, and it took a fraction of a second. For a 32-bit adder the formula is bigger, but nothing like 2<sup>64</sup> tests.

</details>

## A proof that fails

The same assertion on the buggy adder (the 4-bit sum):

<HdlRun design="verification/formal-bug" caption='Proving the buggy adder' predict />

<details>
<summary>Check your answer</summary>

`model found: FAIL!`, with a **counterexample**: a = 6, b = 10, y = 0. 6 + 10 = 16, which a 4-bit sum wraps to 0, so y is smaller than both inputs.

Nobody chose that input: the solver found it. A counterexample is the most useful output a verification tool can give, because it's a concrete case you can simulate, debug and keep as a regression test.

</details>

<KeyIdea>Simulation checks the inputs you run; a formal proof checks them all. When the proof fails, the counterexample is a real input that breaks the rule, ready to debug.</KeyIdea>

## Bounded and unbounded proofs

The adder has no state, so one check covers everything. A design with registers, like a counter, changes over time. Write down what a proof has to cover for such a design, and why it is harder.

<details>
<summary>Check your answer</summary>

For a sequential design, an assertion must hold in every reachable state, after any number of clock cycles.

- A **bounded** proof (bounded model checking) starts from the reset state and checks every possible input sequence for the first N cycles. If it fails, it gives a counterexample trace. If it passes, the rule holds for N cycles, which is not the same as forever.
- An **unbounded** proof uses **induction**: it shows the rule holds after reset, and that if it holds for k cycles in a row, it holds in the next one. That covers every cycle. Induction sometimes needs extra assertions to rule out unreachable states the solver would otherwise consider.

SymbiYosys (`sby`) wraps Yosys and several solvers into this flow: bounded checks, induction proofs, cover statements that show a state is reachable, and counterexample traces as waveforms. Commercial tools such as Cadence Jasper do the same at a larger scale.

</details>
