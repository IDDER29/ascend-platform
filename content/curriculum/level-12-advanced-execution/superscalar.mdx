The five-stage pipeline in Pipelining finishes at most one instruction per cycle: a CPI of 1 at best. To go faster at the same clock rate, a CPU has to start more than one instruction per cycle. A CPU that can is **superscalar**.

## Several per cycle

A superscalar core fetches, decodes and issues several instructions each cycle, and has several execution units (more than one ALU, separate load and store units) to run them side by side. Its **width** is how many it can issue per cycle. Big desktop and phone cores today issue roughly 4 to 8 instructions per cycle.

With more than one instruction per cycle, CPI drops below 1, so it's usually flipped into **IPC**, instructions per cycle:

```
IPC = instructions / cycles     CPI = cycles / instructions = 1 / IPC
```

The lab below schedules a block of instructions on an idealised core. Each row is an instruction; **E** marks the cycles it executes, and **C** the cycle it commits (finishes, in program order). Simple ALU instructions take 1 cycle, a load 3, a multiply 3. This first lab issues in order and leaves out fetch, branches and memory, so you can see issue width on its own.

At width 1 the adds issue in cycles 1 to 8, and the last commits in cycle 9. At width 2 they issue in pairs in cycles 1 to 4, and at width 4 in two groups. The time doesn't halve exactly because the last cycle, when the final results commit, is there whatever the width. Over a long run of independent work that one cycle stops mattering, and IPC approaches the width.

<KeyIdea>A superscalar core issues several instructions per cycle, so IPC can rise above 1, but only when there are several instructions ready to go at once.</KeyIdea>

## What width can't fix

Now four adds where each uses the one before: r1 feeds r4, r4 feeds r5, r5 feeds r6. Predict the time at width 1, 2 and 4.

<OooLab caption='A chain of four adds' blockJson='["add r1, r2, r3","add r4, r1, r1","add r5, r4, r4","add r6, r5, r5"]' optionsJson='{"outOfOrder":false,"width":1,"window":32,"renaming":true}' />

<details>
<summary>Check your answer</summary>

5 cycles at every width. Each add waits for the result of the one before it, so they issue in cycles 1, 2, 3 and 4 however many slots are free. The lab says why on each row: "waits: r1 from add r1, r2, r3", and so on.

How many instructions *could* run at once, given their dependences, is a program's **instruction-level parallelism** (ILP). The chain has an ILP of 1; the independent block has as much as you like. A wide core only helps code that has ILP to give it. Everything in this course is about finding more of it.

</details>

## Pairing them up in order

An **in-order** superscalar issues instructions in program order: it can pair an instruction with the next one only if both are ready. This block has three little pairs, each an add and then an add that uses it. On this two-wide in-order core it takes 5 cycles. Reorder the instructions, without changing what any of them compute, to get it down to 4.

<OooLab editable fixed caption='Schedule for a two-wide in-order core' blockJson='["add r1, r2, r3","add r4, r1, r1","add r5, r6, r7","add r8, r5, r5","add r9, r10, r11","add r12, r9, r9"]' optionsJson='{"outOfOrder":false,"width":2,"window":32,"renaming":true}' goalJson='{"maxCycles":4}' />

<details>
<summary>Check your answer</summary>

Put the three independent first adds together, then the three adds that use them:

```
add r1, r2, r3
add r5, r6, r7
add r9, r10, r11
add r4, r1, r1
add r8, r5, r5
add r12, r9, r9
```

Now cycle 1 issues r1 and r5, cycle 2 issues r9 and r4 (r1 is ready by then), cycle 3 issues r8 and r12, and the last results commit in cycle 4. In the original order each dependent add sat right behind its producer, so most cycles could issue only one.

Moving just one instruction (for example r5's add up one place) still gives 5 cycles: every dependent add must have its producer issued in an earlier cycle. This is the same **instruction scheduling** you did by hand in Pipelining, and compilers do it for in-order cores. The next lesson's out-of-order core does it in hardware, while the program runs.

</details>
