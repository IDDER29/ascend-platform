A C array has a fixed size, chosen when it's created. Real programs rarely know in advance how many items they'll get: lines in a file, words in a text, players in a game. A **dynamic array** solves that: it keeps its items in a heap block, and when the block is full it gets a bigger one.

## A struct with three parts

A dynamic array needs three things, so it's a struct:

```c
typedef struct {
    int *data;   /* the heap block holding the items */
    size_t len;  /* how many items are in use */
    size_t cap;  /* how many fit before we must grow */
} Vec;
```

`len` is what the user sees; `cap` is how much room is already paid for. A push writes at `data[len]` when there's room, and grows the block first when `len == cap`. The vector **owns** its block: whoever made it must call `vec_free` once, and nobody else frees `data`.

## Growing safely with realloc

`realloc(p, size)` returns a block of the new size holding the old contents. It may extend the block where it is, or allocate a new one, copy everything across and free the old one. It can also fail:

```c
static int vec_reserve(Vec *v, size_t new_cap) {
    int *bigger = realloc(v->data, new_cap * sizeof *bigger);
    if (bigger == NULL) {
        return -1;          /* v is unchanged: the old block is still valid */
    }
    v->data = bigger;
    v->cap = new_cap;
    return 0;
}
```

The new pointer goes into a separate variable first. If `realloc` fails it returns `NULL` and leaves the old block alone; writing `v->data = realloc(v->data, ...)` would throw away the only pointer to it. Callers check `vec_push`'s return value in turn, so running out of memory is reported, never ignored.

## Doubling versus growing by one

How much bigger should the new block be? <details>
<summary>Check your answer</summary>

With doubling the capacity goes 1, 2, 4, 8, 16, 32, and 10,000 pushes copied 16,383 items: about 1.6 copies per push. Growing by one copied 49,995,000, about 5,000 per push.

The reason is arithmetic. Doubling copies everything only when it's full, which happens at 1, 2, 4, ..., 8192 items, and 1 + 2 + 4 + ... + 8192 is 16,383, less than 2 copies per push. Each push costs **O(1) on average** (amortised), even though a single push that triggers a grow costs O(n). Growing by one copies 1 + 2 + ... + 9,999 items, about n²/2: **O(n) per push**. For a million items that's half a trillion copies.

The price of doubling is space: just after a grow, up to half the capacity is empty. Some libraries grow by 1.5 times to waste less.

</details>

<KeyIdea>Grow a dynamic array by a factor, not by a fixed amount: doubling makes appends O(1) on average, at the cost of some unused capacity.</KeyIdea>

## A pointer that goes stale

This program keeps a pointer to the first item, then pushes one more item, which makes the array grow. It's built with AddressSanitizer. Predict the second line.

<details>
<summary>Check your answer</summary>

The first line prints 10. The fifth push fills a full array, so `realloc` moves the items to a new, bigger block and frees the old one. `first` still points into the old block, so reading it is a **heap-use-after-free**, which ASan reports at `main.c:33`.

Without ASan this might even print 10: `realloc` sometimes grows a block in place, and freed memory often still holds its old bytes. That's what makes this bug nasty: it works in testing, then fails when the block happens to move. (ASan always moves the block, to catch exactly this.)

The rule: any pointer into a dynamic array is valid only until the next operation that may grow it. Keep an **index** instead, and turn it into a pointer only when you use it: `v.data[i]`.
