A wrong answer tells you something is broken, not where. On the tiny CPU you can see everything, every register and every byte, so you can find exactly where a program goes wrong. The trick is knowing what to look for.

By the end you'll be able to debug a short program one step at a time, and find the step where things first go wrong.

## Predict, then step

Debugging this way is a loop of three moves:

1. **Predict** what the next instruction will change: which register, which box, which flag.
2. **Step** one instruction.
3. **Compare** what happened with what you predicted.

As long as they match, carry on. The first time they don't, you've found where to look. A breakpoint, in a real debugger, is just a way to run quickly up to the part you care about and start stepping there.

## Find the first wrong step

Every step starts from the state the step before left behind. So once one step goes wrong, every later step is working from a wrong state, and the final answer is just the last of many consequences. The useful step is the <b>first</b> one that differs from your prediction.

<KeyIdea>Don't stare at the wrong answer. Find the first step that differs from what you expected.</KeyIdea>

## A worked example

This program should add up the four bytes in boxes 0x80 to 0x83 (3, 4, 5 and 6) and show 18. R2 points at the next byte, R3 counts the bytes left, R1 is the total. It shows 12.

Step through it and predict as you go:

<TruthTable caption='The first steps, predicted and actual' rowsJson='[["step", "instruction", "predicted", "actual"], ["4", "LDR R0, [R2]", "R0 = 3, from box 0x80", "R0 = 3"], ["5", "ADD R1, R0", "R1 = 3", "R1 = 3"], ["6", "DEC R3", "R3 = 3", "R3 = 3"], ["7", "JNZ loop", "jump back to the LDR", "jumped"], ["8", "LDR R0, [R2]", "R0 = 4, from box 0x81", "R0 = 3, from box 0x80"]]' />

Step 8 is the first that differs: the second LDR reads box 0x80 again, because R2 is still 0x80. Yet the LDR itself is fine. The cause is a line that isn't there: nothing moves R2 on to the next box. The program adds 3 four times, giving 12.

The fix is `INC R2` after the ADD. The step where a bug shows up and the line that causes it are often different, and finding the first wrong step is what leads you from one to the other.
