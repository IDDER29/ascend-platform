A set is full and a new line needs a place. Something must go. And when the program writes, the cache must decide when memory hears about it. These two policies are the cache's strategy.

## LRU and FIFO

The two classic replacement policies:

- **LRU (least recently used):** evict the line whose last use is oldest. It bets that the recent past predicts the near future.
- **FIFO (first in, first out):** evict the line that arrived first, however recently it was used. Simpler: no need to update anything on a hit.

Real L1 caches use cheap approximations of LRU (tree pseudo-LRU), because exact LRU for 12 ways needs a lot of bookkeeping per set.

This cache is one set of 2 ways (32 bytes, 16-byte lines). The trace touches lines 0, 16, 0, 32, 0. It starts with FIFO. Predict both policies, then switch so the trace has at most 3 misses.

<details>
<summary>Check your answer</summary>

- **FIFO:** miss, miss, hit, miss, miss: 4 misses. When line 32 arrives, FIFO evicts line 0 because it came in first, even though it was used one access ago. So the last access to 0 misses again.

Switch the policy to "least recently used" to meet the goal. The lab calls the last FIFO miss a *conflict* miss: an LRU cache of the same size would have kept the line.

## LRU's blind spot

LRU isn't always best. A cache that holds 16 lines (1 KiB, 64-byte lines, 4 ways) runs a loop over 24 lines, three times. Predict the hit rate.

<CacheLab caption='A loop slightly too big for the cache' configJson='{"sizeBytes":1024,"lineBytes":64,"ways":4,"policy":"LRU","write":"write-back"}' patternJson='{"start":0,"stride":64,"count":24,"repeat":3}' />

<details>
<summary>Check your answer</summary>

**0 hits in 72 accesses.** After the first pass, each set holds the 4 most recent of its 6 lines. The line needed next is always the one used longest ago, which is exactly the one LRU just evicted. Every access misses: 24 compulsory, then 48 capacity misses. FIFO does the same here.

Two fixes:

- **A bigger cache:** set the size to 2 KiB, and the loop's 24 lines fit, giving 48 hits.
- **Random replacement:** evicting a random way would keep *some* of the loop in the cache and hit part of the time.

Some modern CPUs use adaptive policies that spot this pattern and protect part of the working set.

</details>

<KeyIdea>Replacement is a bet about the future. LRU bets that recently used data is used again; a loop just bigger than the cache breaks that bet completely.</KeyIdea>

## When a write reaches memory

Two policies for stores that hit in the cache:

- **Write-through:** every store also goes to memory (in practice, to a write buffer that drains to memory). Memory is always up to date, at the cost of traffic for every store.
- **Write-back:** the store only updates the cached line and sets its **dirty bit**. The whole line is written to memory once, when it's evicted, and only if it's dirty.

And for stores that miss:

- **Write-allocate:** bring the line into the cache, then write it. That's good when nearby data will be written or read soon.
- **No-write-allocate:** send the store to memory and leave the cache alone. That's good for data written once and never read back.

Most CPU caches are write-back with write-allocate; the lab models both write policies, always with write-allocate. This trace writes 4 ints in line 0, reads 0x100 (which evicts line 0 in this 256-byte direct-mapped cache), then writes line 0 again. Predict the memory writes under each policy, then switch the policy and compare.

<CacheLab caption='Four stores to one line' configJson='{"sizeBytes":256,"lineBytes":16,"ways":1,"policy":"LRU","write":"write-back"}' traceJson='["W 0x0","W 0x4","W 0x8","W 0xC","R 0x100","W 0x0"]' />

<details>
<summary>Check your answer</summary>

- **Write-back:** 1 write-back. The four stores mark line 0 dirty (the sets view shows "D"). Reading 0x100 evicts it, and the whole line is written to memory once. The last store brings line 0 back and leaves it dirty again, with no memory write yet.
- **Write-through:** 5 memory writes, one per store. Nothing is ever dirty, so the eviction costs nothing extra.

The hits and misses are the same either way (3 misses, 3 hits). The policies differ in traffic, and traffic is what limits a multicore chip sharing one memory system. That's a big reason most caches are write-back.

</details>
