In Foundations, a file was a named thing in a folder, built on storage blocks. A Unix file system splits that into two separate things: the **inode**, which is the file itself, and **names**, which are just entries in directories pointing at inodes.

## The inode

An inode is a fixed-size record, one per file, holding everything about the file except its name:

- the type (regular file, directory, symbolic link, device and so on) and the permission bits;
- the owner and group;
- the size, and the timestamps (last access, modification, status change, creation);
- the **link count**: how many names point at it;
- where the data is on the disk (the next lesson is about this).

Each inode has a number, unique within its file system. `stat` shows the inode of a file on this machine's ext4 disk (the owner's name is replaced with `learner` here):

```
$ stat big.bin
  File: big.bin
  Size: 1000000   	Blocks: 1960       IO Block: 4096   regular file
Device: 259,2	Inode: 10535190    Links: 1
Access: (0664/-rw-rw-r--)  Uid: ( 1001/   learner)   Gid: ( 1001/   learner)
Access: 2026-10-31 13:12:09.434941930 +0000
Modify: 2026-10-31 13:12:09.448942046 +0000
Change: 2026-10-31 13:12:09.448942046 +0000
 Birth: 2026-10-31 13:12:09.434941930 +0000
```

Inode 10535190, one link, 1 MB of data, 1960 blocks of 512 bytes allocated. The name `big.bin` isn't in the inode at all.

## Directories map names to inodes

A directory is a file whose contents are a table of entries: a name and an inode number. Opening `/home/learner/notes.txt` means: find the root directory's inode, look up `home` in it to get another inode number, look up `learner` in that, then `notes.txt`. Each step reads a directory. The kernel caches these lookups, because paths are resolved constantly.

So a "file in a folder" is really an entry in a table. Renaming a file within one file system just rewrites entries; the inode and its data never move.

<KeyIdea>The inode is the file: its data, size, owner, permissions and link count. A name is just a directory entry pointing at an inode number.</KeyIdea>

## Hard and symbolic links

Since names are just entries, one inode can have several:

- A **hard link** (`link()`, or `ln a b`) adds another entry pointing at the **same inode**, and the link count goes up.
- A **symbolic link** (`symlink()`, or `ln -s a c`) is a **new inode** of type link, whose contents are a path. Opening it makes the kernel follow that path.
- **`unlink()`** (what `rm` calls) removes one name and lowers the link count. The inode is freed only when no names are left.

The same thing on ext4, in a shell, with real inode numbers:

```
$ ls -li notes.txt hard.txt soft.txt
10535431 -rw-rw-r-- 2 learner learner 6 Oct 31 13:13 hard.txt
10535431 -rw-rw-r-- 2 learner learner 6 Oct 31 13:13 notes.txt
10535433 lrwxrwxrwx 1 learner learner 9 Oct 31 13:13 soft.txt -> notes.txt
$ rm notes.txt
$ cat hard.txt
hello
$ cat soft.txt
cat: soft.txt: No such file or directory
```

`hard.txt` and `notes.txt` show the same number in the first column; `soft.txt` has its own.

The name is gone at once, and `fstat` reports a link count of **0**, yet the write and the read both work: the open descriptor holds the inode. When the program closes it, the kernel finally frees the inode and its blocks.

This is the classic "I deleted the 10 GB log file and the disk is still full" puzzle: a running program still has it open. It's also a useful trick for temporary files: create, unlink, use, and the file vanishes even if the program crashes.
