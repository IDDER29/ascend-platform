The C Language showed undefined behaviour as a list of things not to do: use freed memory, write past an array. This lesson goes underneath: why the standard leaves things undefined at all, what "no requirements" really allows, and how to catch undefined behaviour as a program runs.

## Why leave anything undefined?

C was standardised to run on very different machines, and to be fast on all of them. For each risky operation, the committee had a choice: define one result, and make every compiler produce it on every CPU, or leave it **undefined** and let each compiler do whatever is cheapest, on the condition that correct programs never do it.

Defining a result has a cost. If signed overflow had to wrap, a compiler could no longer assume `i + 1 > i` in a loop, and a number of loop optimisations would be lost. If reading past an array had to report an error, every array access would need a bounds check. C chose speed and put the burden on the programmer: in return, you promise not to do these things.

`INT_MAX + 1` printed `-2147483648`: the `add` instruction wrapped around. But `INT_MIN / -1` never printed. The true answer, 2147483648, doesn't fit in an `int`, and x86's `idiv` instruction responds by raising a hardware exception, which Linux delivers as `SIGFPE`, killing the program.

Both are signed overflow, and both are undefined (C17 6.5 and 6.5.5). On this CPU one wraps and the other crashes, and on another CPU it could be the other way round. That's exactly why the standard doesn't pick a result. And this is only what gcc did with optimisation off: lesson 4 shows a build where gcc never performs the add at all.

## No requirements, for the whole run

"No requirements" is literal. The standard's note says the outcome may range "from ignoring the situation completely with unpredictable results, to behaving during translation or program execution in a documented manner characteristic of the environment, ... to terminating a translation or execution" (C17 3.4.3). Three consequences follow:

1. **It isn't confined to one line.** A program that executes undefined behaviour has no meaning at all. The compiler may produce code that misbehaves before the faulty operation is reached, because it reasons about the whole program on the assumption that the faulty operation never happens.
2. **Compilers use that assumption.** In this code, the dereference on the second line tells gcc that `p` can't be null, so at -O2 it may delete the check on the third (gcc's `-fdelete-null-pointer-checks`, on by default when optimising):

   ```c
   int read_flag(int *p) {
       int value = *p;          /* undefined if p is NULL */
       if (p == NULL) {         /* gcc may assume this is false */
           return -1;
       }
       return value;
   }
   ```

   The check meant to protect against a null pointer comes *after* the dereference that assumes it isn't null. The last lesson in this course, *What the optimiser assumes about your code*, is all about this.
3. **It can change with any change.** A new compiler version, other flags, or an unrelated edit can turn "works" into "fails", because the program was never correct.

<KeyIdea>Undefined behaviour isn't a result; it's the absence of any promise. The compiler assumes it never happens, and reasons about your whole program on that basis.</KeyIdea>

## Catching it as it happens

You can't see undefined behaviour by reading output, but you can **instrument** the program to check. gcc's UndefinedBehaviorSanitizer, `-fsanitize=undefined`, adds a check before each risky operation and prints a report when one goes wrong. UBSan reports each bug with its file, line and column, in the order they happen:

1. `2147483647 + 1 cannot be represented in type 'int'`: signed overflow.
2. `shift exponent 32 is too large for 32-bit type 'int'`: shifting by the width of the type is undefined (C17 6.5.7).
3. `index 4 out of bounds for type 'int [4]'`: writing one past the end of `table`.

By default UBSan reports and keeps going, so the program still printed a line. Look at its second number: `1 << 32` gave `1`, because x86's shift instruction only uses the low 5 bits of the count, so it shifted by 0. Not 0, and not an error: just one more thing undefined behaviour might do.

(This build turns off one UBSan check, `object-size`, whose report prints a memory address that changes on every run.)

</details>

UBSan is easy to add to every debug build, and many teams run their whole test suite under it. But it only finds bugs **on the paths you run**: a bug in a branch your tests never take stays silent. It also doesn't cover everything. AddressSanitizer (`-fsanitize=address`) catches most memory errors, and ThreadSanitizer data races; strict-aliasing violations have no good runtime check.

## A short catalogue

Annex J.2 of the standard lists about 200 kinds of undefined behaviour. These cause most real bugs:

| Undefined behaviour | Where in this course |
|---|---|
| Signed overflow, and `INT_MIN / -1` | Signed overflow and shifts |
| Shifting by a negative count or by at least the width; left-shifting into or past the sign bit | Signed overflow and shifts |
| Modifying a variable twice, or reading it while it's modified, with no sequencing between | Sequencing and order of evaluation |
| Reading an object through a pointer of an incompatible type | Aliasing and strict aliasing |
| Using a dangling pointer, or reading an uninitialised variable | Lifetime |
| Out-of-bounds array access, null dereference | The C Language |
| Modifying a string literal | The C Language (strings) |
| Using the value of a function that ended without `return` | C Basics (functions) |

## Try it

For each, say whether it's undefined, and if so, what a safe version looks like:

1. `int avg = (a + b) / 2;` with `a` and `b` both large positive `int`s.
2. `unsigned avg = (a + b) / 2;` with large `unsigned` values.
3. `int q = x / y;` where `y` comes from user input.

<details>
<summary>Check your answer</summary>

1. **Undefined** if `a + b` exceeds `INT_MAX`. A safe version for non-negative values: `a + (b - a) / 2`, which never overflows when `0 <= a <= b`. (The same overflow sat in Java's binary search for about nine years; Java defines it to wrap, so it gave a negative index instead.)
2. **Defined, but wrong:** unsigned addition wraps, so the sum loses its top bit and the average is garbage. The same `a + (b - a) / 2` fix works for `a <= b`.
3. **Undefined** if `y` is 0, or if `x` is `INT_MIN` and `y` is -1. Check both before dividing.

</details>
