In this project you put a whole data structure into a reusable library: a map from strings to `int`s that grows as it fills. You'll read its interface and implementation, run its tests, break its ownership contract on purpose, and use it from a second program.

## Part 1: The interface

A C library is its header. Everything a user may rely on is here, and nothing else:

```c
/* A map from strings to ints. The map copies every key it stores and frees
   those copies itself; the caller keeps ownership of the keys it passes in. */
typedef struct hashmap hashmap;

hashmap *hm_new(void);                                 /* NULL if out of memory */
void hm_free(hashmap *m);                              /* frees the map and its key copies */
bool hm_put(hashmap *m, const char *key, int value);   /* false if out of memory */
bool hm_get(const hashmap *m, const char *key, int *value);
bool hm_remove(hashmap *m, const char *key);
size_t hm_count(const hashmap *m);
size_t hm_capacity(const hashmap *m);
/* Call fn once for every key and value, in no particular order. */
void hm_each(const hashmap *m, void (*fn)(const char *key, int value, void *ctx), void *ctx);
```

Find three design decisions in it, and say what each protects the user from.

<details>
<summary>Check your answer</summary>

- **`typedef struct hashmap hashmap;` with no fields:** an **opaque type**. Users can only hold a pointer and call the functions, so they can't depend on the layout, and the implementation can change freely.
- **The ownership comment:** the map copies keys and frees its copies, and the caller keeps its own strings. Nobody has to guess who frees what.
- **Every way to fail is visible:** `hm_new` can return `NULL`, `hm_put` returns `false` when memory runs out, and `hm_get` returns whether it found the key, with the value written through a pointer. No call silently fails.

`const hashmap *` on the read-only functions is a fourth: it promises `hm_get` and `hm_count` never change the map.

</details>

## Part 2: Read the implementation

The implementation is a **chained** hash table:

- An array of buckets, each the head of a linked list of entries.
- **FNV-1a** hashes each key. The bucket is the hash's low bits: the number of buckets is a power of two, so `hash & (capacity - 1)` picks one cheaply.
- When a put would take the map past **3/4 full** (entries over buckets), it doubles the buckets and moves every entry to its new bucket. The entries are reused, not copied.

The tests below print its files, `hashmap.c` included. Read `hm_put`, `grow` and `hm_remove`. Why does `hm_remove` walk a pointer to a pointer (`entry **link`) instead of a pointer to an entry?

<details>
<summary>Check your answer</summary>

To unlink an entry, you must change whatever points at it. That's either the bucket's head (`m->buckets[i]`) or the `next` field of the previous entry. `link` always points at that pointer, whichever it is, so one line, `*link = e->next;`, handles both cases. There's no special case for "the first entry in the bucket".

Growth keeps chains short. At most 3/4 of an entry per bucket on average means a lookup compares only a few keys, so `hm_get` is O(1) on average. Doubling costs O(n), but after growing at n entries the map doesn't grow again until it holds 2n, so those O(n) moves are spread over n puts and each put pays O(1) on average: **amortised** constant time. The worst case is still O(n), if every key landed in one bucket. A good hash makes that very unlikely.

</details>

## Part 4: Break the contract

Now a version that "saves memory" by keeping the caller's key pointer instead of a copy. It no longer frees keys, since it doesn't own them. Only `hashmap.c` changed. Predict which test fails, and why.

<CRun program="data-structures/hashmap-bug" caption='The same tests, with keys not copied' show="main.c" predict />

<details>
<summary>Check your answer</summary>

`test_keys_are_copied` fails. The test stores `key`, a local array holding "cat", then changes it to "bat". The map's entry points at that same array, so the entry now says "bat", yet it sits in the bucket for "cat". Looking up "cat" finds an entry with a different key, so the lookup fails, and the `assert` stops the program.

Two more things to notice:

- **The earlier "ok" lines are missing.** `printf` output going to a pipe is fully buffered, and `abort()` (which a failed `assert` calls) ends the program without flushing that buffer. When a program dies, print diagnostics to `stderr`, which is unbuffered, or call `fflush(stdout)` first.
- **In real code this bug is worse.** If the caller's string is freed, the map holds a dangling pointer, and every later lookup in that bucket reads freed memory.

</details>

## Part 5: Use it from another program

A word counter that knows nothing about buckets or chains, only the header. It reads text, counts each word, then uses `hm_each` with a callback to collect the words seen at least twice, and sorts them.

<CRun program="data-structures/hashmap-wordcount" caption='Counting words with the library' show="main.c" predict />

<details>
<summary>Check your answer</summary>

26 different words, with "a" 7 times and "map" 5 times, then the words seen twice. Note the details that make it correct and repeatable:

- **Counting:** `hm_get` leaves `n` at 0 for a new word, so one `hm_put(m, word, n + 1)` both adds and updates.
- **The callback:** `hm_each` passes a `void *ctx` through to the callback, so `collect` can fill an array without any global variable.
- **The order:** the map promises no order, so `qsort` sorts by count, then alphabetically. The output would otherwise depend on bucket layout and could change if the hash or capacity changed.
- **Cleanup:** `collect` stores the map's own key pointers, which stay valid until `hm_free`. That's why `free(c.items)` comes before `hm_free(m)`, and it runs leak-free under ASan.

</details>

<KeyIdea>A library is a contract: an opaque type, a header that says who owns what and how each call can fail, and tests that prove the promises, run under sanitizers.</KeyIdea>
