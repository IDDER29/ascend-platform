This program reads up to 8 scores and prints how many there were, their average, the best one with its letter grade, and a bonus that doubles every 3 points. It compiles. With five ordinary scores it even prints the right count and the right best score. It also contains **five** pieces of undefined behaviour.

## Part 1: Read it first

Read the program and list every line that may be undefined, and for which inputs. Don't run anything yet. The build below is just to show it compiles; scroll past its output for now.

<CRun program="c-contract/ub-hunt-warnings" caption='The program, built with -O2 -Wall -Wextra' />

<details>
<summary>Check your answer</summary>

1. **`return label;`** returns the address of a local array. Its lifetime ends when `grade` returns, so the caller gets a dangling pointer.
2. **`while (n <= MAX_SCORES ...`** lets `scanf` write `scores[8]`, one past the end, when 9 or more scores are typed.
3. **`int total;`** is never initialised, and `total += ...` reads it.
4. **`1 << (best / 3)`**: for a best of 93 or more the shift is 31, and 2 to the 31 doesn't fit in an `int`. For a score of 96 or more it's 32, a shift by the full width, which is also undefined.
5. **`total / n`** divides by zero when there are no scores, and `int best = scores[0]` reads an uninitialised element then too.

</details>

## Part 2: What the builds say

The build above is **-O2 -Wall -Wextra**. gcc warned about two of the five: the returned local address, and `total` being used uninitialised. (That second warning needs optimisation: gcc's data-flow analysis only runs then, and an -O0 build of the same file stays silent.) The output looks almost right, but `best: 95 ((null))` and the negative bonus are clues: gcc replaced the dangling pointer with a null pointer, which glibc's `printf` prints as `(null)`.

Now the same program built with **AddressSanitizer and UndefinedBehaviorSanitizer**, which check the program while it runs, on three inputs. Predict what each run reports before you open it.

<CRun program="c-contract/ub-hunt-five" caption='Five scores, with sanitizers' predict />

<CRun program="c-contract/ub-hunt-many" caption='Nine scores, with sanitizers' predict />

<CRun program="c-contract/ub-hunt-empty" caption='No scores, with sanitizers' predict />

<details>
<summary>Check your answer</summary>

- **Five scores:** UBSan reports the shift: "left shift of 1 by 31 places cannot be represented in type 'int'", at `main.c:34`. The average comes out as a large negative number here, because `total` started with garbage in this build. With -O2 it printed 81, and at -O0 without sanitizers 82: three builds, three answers, and only 81 is right (406 / 5). That's undefined behaviour: the program has no single meaning.
- **Nine scores:** ASan stops the program at the 9th `scanf`, with a **stack-buffer-overflow** WRITE of 4 bytes at `main.c:22`. Without ASan, that write would silently overwrite whatever lives next to `scores`.
- **No scores:** UBSan reports **division by zero** at `main.c:37`, and the CPU's divide instruction then raises a floating-point exception (the signal is called that even for integers), which stops the program.

None of the tools found everything on its own. Warnings found two bugs without running anything. The sanitizers found three more, but only for the inputs that triggered them. That's why the hunt needs both, plus inputs chosen to reach the edges: empty, too many and the largest values.

</details>

## Part 3: Fix every one

Write down a fix for each of the five, then compare with this version. It's built with both sanitizers and given 10 values, one of them out of range.

<CRun program="c-contract/ub-hunt-fixed" caption='The fixed program, with sanitizers' predict />

<details>
<summary>Check your answer</summary>

1. `grade` returns string literals. They have **static storage duration**: they live for the whole program, so returning a pointer to one is safe.
2. Values are read into a temporary, and stored only while `n < MAX_SCORES`. Extra scores are reported and skipped, never written past the end.
3. `int total = 0;`.
4. Scores outside 0 to 100 are rejected, so `best / 3` is at most 33, and the shift is done on `1LL`, which has 63 value bits. 2 to the 33 fits easily.
5. No scores means "no scores" and exit status 1, before `scores[0]` or the division is touched. Here's that path, also under both sanitizers:

<CRun program="c-contract/ub-hunt-fixed-empty" caption='The fixed program, no scores' />

The sanitizers report nothing for either input, and the average of the 8 accepted scores (622 / 8) is 77. A clean run proves only that these inputs are safe. The reasoning in each fix is what makes every input safe.

</details>

## Part 4: Say why it was legal to break

For two of the five bugs, say what the compiler was *allowed* to do because the behaviour was undefined. Use what you saw.

<details>
<summary>Check your answer</summary>

- **The dangling pointer:** the standard says nothing about what happens when you use a pointer to an object whose lifetime is over, so gcc was free to return a null pointer instead of the address. It did, and that's why the output said `(null)`. A different compiler might return the real address and print garbage, or crash.
- **The uninitialised `total`:** an uninitialised automatic variable has an indeterminate value, and reading it is undefined here, so gcc can use whatever is in the register or memory it picked. At -O0 and -O2 that happened to differ, and the averages did too.

Any of the other three works too: an overflowing shift may produce any value, an out-of-bounds write may corrupt anything, and division by zero may crash or not. The compiler isn't misbehaving in any of these cases: the program left the contract.

</details>

<KeyIdea>Hunt undefined behaviour by reading first, then with -O2 warnings and the address and undefined-behaviour sanitizers on edge-case inputs. Fix each case by reasoning about every input, not just the ones you tried.</KeyIdea>
