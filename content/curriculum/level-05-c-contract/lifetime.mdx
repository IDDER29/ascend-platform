The C Language showed you storage duration: automatic objects live in a function's frame, static ones for the whole run, allocated ones until `free`. This lesson is about the exact rule that sits under all three, and the two bugs that break it most often.

## What lifetime means

C17 6.2.4p2 defines an object's **lifetime** as the part of the program's run during which storage is guaranteed to be reserved for it. During its lifetime an object has a constant address and keeps its last-stored value. Then two sentences that matter here:

- If an object is referred to outside of its lifetime, the behaviour is undefined.
- The value of a pointer becomes **indeterminate** when the object it points to reaches the end of its lifetime.

For an ordinary automatic variable, the lifetime runs from entry into its **block** until execution of that block ends. Not the function: the block, the `{ ... }` it was declared in.

The second sentence is the surprising one. The pointer itself isn't changed, and the bytes it points at may still be there. But the standard says you may not use its value any more. A dangling pointer isn't a pointer to garbage; it's a pointer you're not allowed to use at all.

<KeyIdea>An object's lifetime ends when its block ends, its function returns, or it is freed. After that, every pointer to it is indeterminate, whatever the memory still holds.</KeyIdea>

## Returning the address of a local

This is the most common way to make a dangling pointer:

<CRun program="c-contract/lifetime-return-local" caption='Returning a pointer to a local' predict />

<details>
<summary>Check your answer</summary>

gcc warns `function returns address of local variable`, and the program is killed by a segmentation fault. You might have expected 42, or garbage, since the frame's memory is still there for a moment. It crashed because gcc, knowing the returned pointer can never be used legally, returns a null pointer instead. This is what `make_answer` compiled to at -O0:

```
movl	$42, -12(%rbp)
movl	$0, %eax
```

It stores 42 in the frame and then returns 0. `main` then reads through a null pointer and crashes. A crash is the kindest outcome undefined behaviour can give you; other compilers may hand back the stale address and print 42 for years.

The fixes depend on who should own the value: return the `int` itself, write into a buffer the caller provides, use a `static` object, or `malloc` it and make the caller free it.

</details>

<details>
<summary>Check your answer</summary>

The first call printed 12, correct by luck: `sum`'s stack slot happened to hold 0. Then `busy` used the same stack area, and the second call started from whatever was left there. The second number is different on every run (on three runs here it was -529586164, 1973855756 and 209830156), because part of what's left on the stack depends on where the operating system placed it.

There was no warning. At -O0 gcc doesn't do the analysis that finds this.

</details>

Now the identical source at -O2:

<CRun program="c-contract/lifetime-uninit-O2" caption='The same program at -O2' />

With optimisation on, gcc does the data-flow analysis and warns three times: `may be used uninitialized` for `total` itself, then `is used uninitialized` for each of the two places it was inlined into `main`. The output changed too: this build printed 12 both times. Which output is "right"? Neither. C17 6.3.2.1p2 says that reading an automatic object that was never initialised and whose address is never taken (one that "could have been declared with the register storage class") is undefined behaviour. `sum` is exactly that.

Two habits follow: initialise every variable where you declare it, and compile at least once with optimisation and `-Wall -Wextra`, because some warnings only exist there.

## Try it

Which line creates the dangling pointer, and when does it become a bug?

```c
#include <stdio.h>
#include <string.h>

const char *greeting(int formal) {
    char text[32];
    strcpy(text, formal ? "Good evening" : "Hi");
    return text;
}

int main(void) {
    puts(greeting(1));
    return 0;
}
```

<details>
<summary>Check your answer</summary>

`return text;` returns the address of a local array. `text`'s lifetime ends when `greeting` returns, so the pointer `main` receives is indeterminate before `puts` even starts. gcc warns `function returns address of local variable` here too. Fix it by making `text` `static` (one shared buffer, fine for a single-threaded program), by returning a string literal directly (`return formal ? "Good evening" : "Hi";`), whose storage is static, or by letting the caller pass in a buffer.

</details>
