You've built every piece separately: bits, gates, memory, a CPU, assembly, a translator, and the OS around them. This lesson puts them in one line. First, a tiny-language program through our own pipeline, every stage visible. Then the same kind of journey for real C on Linux, which you can only partly see.

## The program

```
var n = 4;
var t = 0;
while (n != 0) {
  t = t + n;
  n = n - 1;
}
output(t);
```

It adds 4 + 3 + 2 + 1 and outputs 10. Open each stage of the explorer below in turn. Then change the program so it outputs 15 instead, and run it again.

## Stage by stage

1. **Source.** Text in the tiny language: characters, stored as bytes like any text.
2. **Translate.** Our translator turns each line into tiny CPU assembly: 19 instructions, with labels `while1` and `endwhile1` for the loop. It gives n box 0x80 and t box 0x81.
3. **Assemble.** The assembler gives each instruction an address (0x00, 0x02, ...) and two bytes. `LDI R0, 4` becomes `08 04`; `STA R0, [0x80]` becomes `18 80`.
4. **Load.** The 38 bytes are copied into memory from 0x00. PC starts at 0x00.
5. **Run.** The CPU fetches, decodes and executes, one instruction at a time: 58 steps. Each loop trip reads n and t from memory, adds, and writes them back.
6. **Output.** `OUT R0` sends 10 to the modelled display.

Every stage is something you've built or used in Foundations: the translator in From Source to Machine, the assembler in Assembly Language, the fetch and execute cycle in Build a CPU, the gates underneath in Logic &amp; Circuits.

<KeyIdea>A program's output is the end of a chain: source, translation, bytes, memory, execution, device. Each stage only does what the one before it set up.</KeyIdea>

## What the tiny CPU simplifies

The tiny CPU is a real design that really runs, but it leaves out most of what a real computer has. Be precise about what's missing:

<TruthTable caption='The tiny CPU next to a real computer' rowsJson='[["", "tiny CPU (version 2)", "a real computer"], ["memory", "256 bytes, one real box per address", "gigabytes, reached through virtual addresses and an MMU"], ["programs", "one at a time, from 0x00 to HALT", "hundreds of processes sharing cores, switched by the OS"], ["output", "OUT sends a byte straight to a display", "programs ask the kernel with a system call; drivers talk to devices"], ["protection", "none: no user mode, any program can touch anything", "user and kernel mode, per-process address spaces"], ["loading", "bytes copied to 0x00", "the OS loader maps an executable file, links libraries, starts at _start"], ["storage", "none", "files on disks, through a file system"], ["speed", "one instruction at a time", "pipelines, caches, several instructions at once"]]' />

So: on the tiny CPU, `OUT` is not a system call, and its PC is not a virtual address. Mixing the two pictures up is the most common mistake when people first connect a teaching machine to a real one.

<details>
<summary>Check your answer: someone says "a real CPU is just the tiny CPU with more memory". Name three things that's missing.</summary>

Any three of: privilege modes (user and kernel), address translation (an MMU and per-process address spaces), an operating system that shares the CPU and does I/O through system calls, interrupts, caches, files and storage, and a loader that maps programs and libraries. More memory alone gives you none of them.

</details>

## The same journey in real C

Now a real program. This is the sum-to-n evidence from From Source to Machine, compiled by gcc for x86-64 Linux:

<CompilerOutput evidence="sum-to-n" fn="sum_to" />

The journey has the same shape, with more stages and more hidden:

1. **Source**: a `.c` file, run through the preprocessor (`#include <stdio.h>` pulls in printf's declaration).
2. **Compile and assemble**: gcc makes x86-64 instructions, as above, into an object file.
3. **Link**: the linker joins it with the C library's startup code and printf, into an executable file.
4. **Load**: the shell asks the kernel to run it (`execve`). The kernel creates a process with its own virtual address space and maps the file into it; the loader joins the shared C library.
5. **Run**: the CPU runs `_start`, then main, then sum_to, in user mode, through virtual addresses, sharing cores with everything else.
6. **Output**: printf ends in a system call. The kernel hands the bytes to the terminal, which draws "55".

`strace` shows the moments this process crossed into the kernel (gcc 15.2 on Linux; details differ by system):

```
execve("./sum", ["./sum"], 0x7ffd3c485150 /* 73 vars */) = 0
write(1, "55\n", 3)                     = 3
exit_group(0)                           = ?
+++ exited with 0 +++
```

Those are three of the 34 system calls this short run made; the rest are the loader and the C library setting up. Compare: the tiny program needed none, because it had no OS to ask.

<details>
<summary>Check your answer: in each pipeline, what actually turns the number into something on a screen?</summary>

Tiny CPU: the `OUT R0` instruction itself sends the byte to the modelled display; there is no OS in between. Real C: printf formats "55\n" in the program's memory, then the `write` system call traps into the kernel, which passes the bytes to the terminal program and on to the display hardware. The program never touches the device.

</details>
