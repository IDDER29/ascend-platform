The last lesson said apps reach the hardware only through the kernel. That's not a polite agreement. The CPU enforces it, and the way apps cross the line is one carefully guarded instruction.

By the end you'll be able to say what user and kernel mode are, follow a system call step by step, and read a real trace of one.

## Two modes

Real CPUs have a **mode** bit (some have more than two settings, but two are enough here):

- In **kernel mode**, the CPU will run any instruction: talk to devices, change memory protection, switch modes.
- In **user mode**, those **privileged** instructions are refused. If an app tries one, the CPU doesn't do it: it raises a fault and jumps into the kernel, which usually ends the app.

The kernel runs in kernel mode; every app runs in user mode. An app can't simply switch itself into kernel mode, because switching mode is itself privileged.

Here's a real C program that tries to talk to a hardware port directly, with the x86 instruction `outb`:

```c
#include <stdio.h>

int main(void) {
    printf("before\n");
    fflush(stdout);
    __asm__ volatile ("outb %%al, $0x80" : : "a"(0));
    printf("after\n");
    return 0;
}
```

```
$ ./priv
before
Segmentation fault         (core dumped)
```

The CPU refused the instruction in user mode, and Linux stopped the program with a signal (the label "segmentation fault" is Linux's catch-all name for it). `after` never printed. This is a real run with gcc 15.2 on x86-64 Linux; the exact message depends on the system and shell.

<KeyIdea>The CPU itself enforces the line: privileged instructions work only in kernel mode, and apps always run in user mode.</KeyIdea>

## Asking the kernel: a system call

So how does an app show text or save a file? It makes a **system call**:

1. The app puts a number saying which service it wants (write, open, exit...) and the arguments in registers.
2. It runs the one instruction made for this (`syscall` on x86-64). The CPU **traps**: it saves where the app was, switches to kernel mode, and jumps to the kernel's entry point, a fixed address the kernel chose at startup. The app can't choose where it lands.
3. The kernel checks the request, does the work (often telling a device driver what to do), and puts a result in a register.
4. The kernel returns: the CPU switches back to user mode and the app carries on from the next instruction.

The app gets the service; it never gets kernel mode.

## The kernel checks everything

The kernel can't trust what an app passes in. Before doing anything, it checks: is this file open for this program? Is this buffer address inside the app's own memory? If not, it refuses and returns an error instead of doing harm.

The app's memory in this model runs from 0x4000 to 0x7FFF. Step through it: the first write is fine, the second points outside the app, and the third uses a file descriptor that was never opened. The app keeps running after the refusals; it just gets an error back.

## Real system calls on Linux

`strace` runs a program and prints every system call it makes. Here's the classic first C program, `printf("hi\n")`, traced (a real run; output differs by system):

```
$ strace -e trace=write,exit_group ./hello
write(1, "hi\n", 3)                     = 3
exit_group(0)                           = ?
+++ exited with 0 +++
```

`printf` is a library function that runs in user mode. It collects the text, then makes one `write` system call to file descriptor 1 with 3 bytes, and the kernel returns 3. Then `exit_group` ends the process. Counting every call, not just those two:

```
$ strace -c ./hello
...
100.00    0.001028          30        34         1 total
```

34 system calls for one line of output. Most of them (`execve`, `mmap`, `openat` and others) are the OS loading the program and the C library before `main` even starts.

## The toy and the real thing

The tiny CPU's `OUT` is not a system call. The tiny CPU has no modes, no kernel and no checks: `OUT R0` simply copies a register to the output port, and any program may do it. That's like a real machine running entirely in kernel mode with no OS, which is how very simple computers and microcontrollers really do work.

So when you see `OUT` in a tiny CPU program, think "device instruction". When you see `write` in a trace, think "a request to the kernel, across the line".
