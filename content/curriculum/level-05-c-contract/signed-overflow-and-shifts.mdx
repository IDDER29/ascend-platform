You know from C Basics that an `int` holds a limited range. This lesson is about exactly what C promises when an integer operation leaves that range, why the obvious way to check for it can silently fail, and how to do it right.

## The rules, exactly

| Operation | Signed types | Unsigned types |
|---|---|---|
| `+`, `-`, `*` past the range | **Undefined** (C17 6.5p5) | Defined: wraps modulo 2 to the width (6.2.5p9) |
| `/` or `%` by zero | **Undefined** | **Undefined** |
| `INT_MIN / -1`, `INT_MIN % -1` | **Undefined** (6.5.5p6) | n/a |
| Converting an out-of-range value to the type | Implementation-defined (6.3.1.3) | Defined: wraps |

C23 now requires signed integers to be stored in two's complement, but it did **not** make signed overflow defined. Knowing the bit pattern doesn't make `INT_MAX + 1` legal.

Remember the integer promotions, too: `unsigned char` and `unsigned short` operands are promoted to `int` before arithmetic, so even "unsigned" arithmetic on small types can overflow a signed `int`.

With `-fwrapv`, gcc treats signed overflow as wrapping (a gcc extension, not standard C), so the check works and returns 1. Under UBSan, gcc computes the addition so it can check it, reports the overflow, and the wrapped result makes the function return 1. These results are only what this gcc did with these flags; the program's behaviour is undefined, and none of them is promised.

<KeyIdea>Never check for overflow by doing the overflowing operation and looking at the result. The compiler assumes signed overflow can't happen, so it may delete the check.</KeyIdea>

## Checking without overflowing

The fix is to test **before** computing, using limits from `<limits.h>`, so no operation ever overflows. C23 also adds `<stdckdint.h>`, whose `ckd_add`, `ckd_sub` and `ckd_mul` do the operation and tell you whether it fitted. gcc and clang have long offered the same as `__builtin_add_overflow`.

<details>
<summary>Check your answer</summary>

`add_would_overflow(INT_MAX, 1)` is 1 and `add_would_overflow(100, 1)` is 0. The test `a > INT_MAX - b` (for positive `b`) can't overflow, because `INT_MAX - b` is always in range. The negative case mirrors it with `INT_MIN - b`.

`ckd_add(&sum, INT_MAX, 1)` returns true: it overflowed. `ckd_add(&sum, 40, 2)` returns false and stores 42. The `ckd_` macros are defined for every input, so they're the simplest correct choice where C23 is available.

</details>

## The rules for shifts

For `E1 << E2` and `E1 >> E2` (C17 6.5.7):

- A shift **count** that is negative, or at least the width of the (promoted) left operand, is **undefined**, for signed and unsigned types alike. `x << 32` on a 32-bit type is undefined, not 0.
- **Left-shifting a signed value** is defined only if the value is non-negative and the result fits. `1 << 31` on a 32-bit `int` and `-1 << 1` are both undefined.
- **Right-shifting a negative value** is implementation-defined. gcc shifts in sign bits, so `-8 >> 1` is `-4`.
- **Unsigned shifts** with a valid count are always defined: `1u << 31` is 2147483648.

The safe recipe: shift **unsigned** values (`uint32_t`, `uint64_t`), and keep counts in range. Predict the four lines of this rotate function, which follows both rules.

<details>
<summary>Check your answer</summary>

- `rotl32(0x80000001, 1)` is `00000003`: the top bit wraps around to the bottom.
- `rotl32(0x12345678, 8)` is `34567812`: the top byte moves to the bottom.
- `rotl32(0x12345678, 32)` is `12345678`: `n &= 31` turns 32 into 0, and `(32 - n) & 31` keeps the other shift at 0 too, so no shift is ever by 32.
- `1u << 31` is `2147483648`.

Without the masks, a rotate by 0 or 32 would shift by 32 and be undefined. gcc recognises this pattern and compiles it to a single `rol` instruction.

</details>

## Try it

Each line has a problem with a 32-bit `int`. Name it and fix it.

1. `int bytes = count * size; char *buf = malloc(bytes);`
2. `int mask = 1 << bit;` where `bit` can be 0 to 31.
3. `if (len + offset < len) return ERROR;` where both are `int`.

<details>
<summary>Check your answer</summary>

1. `count * size` can overflow, which is undefined, and a wrapped, too-small size makes a buffer overflow likely. Use `size_t` and check first: `if (size != 0 && count > SIZE_MAX / size) return ERROR;`, or `ckd_mul`.
2. `1 << 31` is undefined for `int`. Use `uint32_t mask = UINT32_C(1) << bit;`.
3. This is the deleted check from above: gcc may fold it to false. Test before adding: `if (offset > 0 && len > INT_MAX - offset) return ERROR;`.
