gcc reads your whole program before it builds anything, and it tells you exactly what it couldn't understand or didn't like. This lesson is about reading what it says. Every message below is real gcc 15 output for the program shown.

## Anatomy of a message

<CRun program="c-basics/err-undeclared" caption='A misspelled name' />

Read the first message piece by piece:

- `main.c:6:9:` is the file, line 6, column 9.
- `error:` means gcc can't build a program at all. (A `warning:` means it can, but suspects a mistake.)
- `'totl' undeclared (first use in this function)` is the problem: there's no variable called `totl`.
- Below it, gcc quotes the line, puts a caret `^~~~` under the exact spot, and here even suggests the fix: `did you mean 'total'?`

The `note:` lines add detail. Here gcc says it reports each undeclared name once per function, so one typo doesn't produce a page of errors.

## The error points after the mistake

<CRun program="c-basics/err-semicolon" caption='A missing semicolon' />

The error is reported on line 5, at `printf`, but line 5 is fine: the semicolon is missing from the end of line 4. gcc only learns a statement wasn't finished when it reaches the next token, so it reports where it noticed, not where you went wrong. When an error makes no sense on its own line, look at the line before.

The second message is a side effect: because the declaration of `count` was never finished, gcc thinks `count` is never used. Fix the first error and this one disappears too.

So always start at the top. Later errors are often echoes of earlier ones; fixing them first wastes time.

## A missing include

<CRun program="c-basics/err-no-include" caption='printf without stdio.h' />

Without `#include <stdio.h>` the compiler has no declaration of `printf`. Since gcc 14 that's an error by default (`implicit declaration of function`). The `note:` lines say exactly what to do, and the `+++ |+#include <stdio.h>` line is a fix-it hint: the line to add, and where. Older compilers only warned here and then guessed `printf`'s type, which is why old tutorials sometimes "work" without the include.

## Warnings are bugs waiting

This program compiles with two warnings. Predict what it prints, then run it.

<CRun program="c-basics/warn-format" caption='It compiled, so it works?' predict />

<details>
<summary>Check your answer</summary>

It prints a meaningless number, here 546760040, and a different one on another machine or run. `%d` tells `printf` to read an `int`, but a `double` was passed, and on x86-64 the two even travel in different registers, so `printf` reads whatever happened to be in the integer one. gcc said exactly this, and even suggested `%f`. The second warning, an unused variable, is harmless here but often means a typo.

The fix is `%f`. The habit is bigger: compile with `-Wall -Wextra`, and fix every warning before running. Many teams add `-Werror`, which turns warnings into errors.

</details>

## Try it

This compiles with a warning, and the output looks plausible. What is the bug, and what did the programmer mean?

<CRun program="c-basics/warn-assign-in-if" caption='Still playing?' />

<details>
<summary>Check your answer</summary>

`if (lives = 3)` assigns 3 to `lives`, and the value of an assignment is the value assigned, 3, which is true. So the condition is always true and `lives` is overwritten. The programmer meant `if (lives == 3)`, which compares and prints nothing here, since lives is 0. gcc's hint, "suggest parentheses around assignment used as truth value", is its way of saying "did you mean ==?"; you'd only add the extra parentheses if the assignment really was intended.

</details>

<KeyIdea>Read the first message, at its file, line and column; if the line looks fine, look just before it. Errors stop the build, warnings let a bug through: fix both.</KeyIdea>

## Done when

You can read a message's position and kind, fix a missing semicolon, an undeclared name and a missing include from the message alone, and you build with `-Wall -Wextra` and fix every warning.
