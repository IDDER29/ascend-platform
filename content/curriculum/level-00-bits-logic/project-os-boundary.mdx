An app can compute on its own, but to show something, save something or touch any device it has to ask the operating system. In this guided lab you follow two requests across that boundary, then see what happens when an app tries to skip it.

The lab is a teaching model of a real OS, not a kernel running on the tiny CPU. Each step is labelled with who does it: the **App**, the **CPU** switching modes, the **Kernel**, or a **Device**.

## Part 1: A line on the screen

Step through this program one step at a time. For each step, say who does it before you read the label.

<SyscallLab caption='Showing hello on the screen' startJson='["compute builds the message", "write 1 \"hello\"", "exit 0"]' />

<details>
<summary>Check your answer</summary>

- **compute** stays in user mode: the app uses its own registers and memory, no OS needed.
- **write(1, "hello")**: the app puts the call and its arguments in registers (App). The trap switches to kernel mode (CPU). The kernel checks that descriptor 1 is the screen and the buffer is the app's own (Kernel). The display driver hands the bytes to the display controller (Device). The kernel returns 5, the number of bytes written, and the CPU switches back to user mode (CPU).
- **exit(0)**: one more trap. The kernel frees the process and records its exit code.

The app never touches the display. It asks, and the kernel does the work with a driver.

</details>

## Part 2: Save a file

This program means to save "saved" in notes.txt. Step it to the end and look at the RAM cache and the disk. Then change the program so the file really is on the disk.

<SyscallLab editable caption='Saving a file' startJson='["open \"notes.txt\"", "write 3 \"saved\""]' goalJson='{"disk":{"notes.txt":"saved"}}' />

<details>
<summary>Check your answer</summary>

After `write 3 "saved"` the text is only in the kernel's RAM cache: the write returned 5, but the disk hasn't changed. Add `close 3` (or `sync`, or `exit 0`, which closes everything): in this model, the storage controller then writes the file to the disk.

Real systems keep writes in RAM too, because RAM is far quicker than storage, and they are lazier than this model: Linux may keep a closed file's new data in RAM for several seconds and write it back later. Only `sync` or `fsync` makes the kernel write it now. That's why a sudden power cut can lose a file you just "saved", and why programs that must not lose data call `fsync`.

</details>

## Part 3: Skipping the OS

This app wants to put the letter H (72) on the screen, and tries to drive the display port itself with `out`. Run it, then fix it so the screen shows H and the kernel doesn't stop the app.

<SyscallLab editable caption='Talking to a device directly' startJson='["compute decides to show H", "out 1 72", "exit 0"]' goalJson='{"screen":"H","notKilled":true}' />

<details>
<summary>Check your answer</summary>

`out` is a privileged instruction. In user mode the CPU refuses it and traps to the kernel, which stops the program. Nothing after it runs, not even `exit`. Replace it with a request: `write 1 "H"`.

If any app could drive devices directly, one buggy or hostile program could scribble over the disk or another program's window. Making device access privileged, and checking every request in the kernel, is what keeps programs apart.

</details>

## Part 4: Model or machine?

Which of these does the tiny CPU (version 2) really have, and which exist only in this lab's model: user and kernel mode, the OUT instruction, a kernel, file descriptors, a disk?

<details>
<summary>Check your answer</summary>

The tiny CPU really has `OUT`, and any program on it may use it: there's no user mode, no kernel, and nothing is privileged. User and kernel mode, the kernel's checks, file descriptors, the RAM cache and the disk are all part of the model, which follows how a real OS such as Linux works, much simplified. The model shows *who does what*, not how a real kernel is built.

</details>

<KeyIdea>An app asks; the kernel checks and acts; devices do the work. The trap into kernel mode is the only door between them.</KeyIdea>
