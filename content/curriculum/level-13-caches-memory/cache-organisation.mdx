In Machine & Memory you saw *that* caches work: programs reuse data, and data near data. This course is about *how* they're built. A cache has to answer one question in a cycle or two: "is this address here, and where?" Its organisation is the answer.

## Lines, sets and ways

A cache stores memory in **lines** (also called blocks): fixed chunks, 64 bytes on almost every modern CPU. Loading one byte brings in its whole line, which is why neighbouring data comes almost free.

Lines are grouped into **sets**. An address maps to exactly one set, and the line can sit in any of that set's **ways**:

- **Direct-mapped:** 1 way. Each address has exactly one possible place. Cheap and fast, but two hot addresses that map to the same place keep evicting each other.
- **N-way set-associative:** N places per set. The hardware compares the tag against all N ways in parallel.
- **Fully associative:** one set containing every line. The fewest conflicts, but a comparator for every line, so it's only practical for small structures like the TLB.

The size is always **sets × ways × line size**.

## Splitting an address

To find a line, the cache cuts the address into three fields:

```
| tag                       | index        | offset     |
  which line in the set       which set      which byte in the line
```

- **offset** = the low log2(line size) bits
- **index** = the next log2(sets) bits
- **tag** = everything above; it's stored with the line and compared on every lookup

Take a 32 KiB cache with 64-byte lines and 8 ways: 32768 / (64 × 8) = **64 sets**, so 6 offset bits, 6 index bits and, for a 32-bit address, a 20-bit tag. Split the address 0x12345678.

<details>
<summary>Check your answer</summary>

The low 12 bits are 0x678 = 0110 0111 1000 in binary.

- **offset** = the low 6 bits, 111000 = 56
- **index** = the next 6 bits, 011001 = 25
- **tag** = 0x12345678 shifted right by 12 = 0x12345

So the byte is at offset 56 of a line in set 25, and that line is a hit only if one of set 25's 8 ways holds tag 0x12345.

</details>

<KeyIdea>An address is tag, index and offset. The index picks the set, the ways are compared against the tag, and the offset picks the byte. Size = sets × ways × line size.</KeyIdea>

## When two lines fight over one set

Now a program alternates between two addresses, 0x000 and 0x100. They're 256 bytes apart, so in this 256-byte cache they have the same index (set 0) and different tags. Run it as given. Then change the cache, keeping its size at 256 bytes, so the trace has at most 2 misses.

<details>
<summary>Check your answer</summary>

Direct-mapped, every access misses: 2 compulsory misses and then 6 **conflict** misses, because each line evicts the other from set 0 even though the other 15 sets sit empty. Choose 2 ways: the cache now has 8 sets of 2 ways, both lines live in set 0 at once, and the trace has only its 2 compulsory misses, then 6 hits.

This is the classic trouble with power-of-two strides. Arrays whose rows are a large power of two apart can map every row to the same few sets.

</details>

## Three kinds of miss

Every miss is one of the **3 Cs**:

- **Compulsory:** the first access to a line. Only prefetching or bigger lines avoid it.
- **Capacity:** the working set is bigger than the whole cache. Even a fully associative cache of the same size would miss. Only a bigger cache helps.
- **Conflict:** the cache had room, but the line's set didn't. More ways help, or a different layout of the data.

The lab classifies each miss the same way, by also running a fully associative LRU cache of the same size and checking whether it would have hit.

## A real CPU's caches

This is the laptop that compiled every program in this course, a 13th-generation Intel Core i5-1335U, read from Linux (`lscpu`, then `/sys/devices/system/cpu/cpu*/cache/`; trimmed):

```
$ lscpu | grep -i cache
L1d cache:                               352 KiB (10 instances)
L1i cache:                               576 KiB (10 instances)
L2 cache:                                6.5 MiB (4 instances)
L3 cache:                                12 MiB (1 instance)

cpu0  L1 Data         48K  ways=12  line=64  sets=64     shared with cpu 0-1
cpu0  L2 Unified    1280K  ways=10  line=64  sets=2048   shared with cpu 0-1
cpu0  L3 Unified   12288K  ways=12  line=64  sets=16384  shared with cpu 0-11
cpu4  L1 Data         32K  ways=8   line=64  sets=64     shared with cpu 4
cpu4  L2 Unified    2048K  ways=16  line=64  sets=2048   shared with cpu 4-7
```

It's a **hybrid** chip: cpu0 is a performance core (two hardware threads share its caches), cpu4 an efficiency core, and they have different L1 and L2 caches. Check one line of it, and notice something about both L1 data caches.

<details>
<summary>Check your answer</summary>

cpu0's L1: 64 sets × 12 ways × 64 bytes = 49152 bytes = 48 KiB. Its L3: 16384 × 12 × 64 = 12 MiB, shared by all 12 hardware threads.

Both L1 data caches have **64 sets of 64-byte lines**, so 6 + 6 = 12 bits of index and offset, and 2^12 = 4096 bytes, exactly one page. That's deliberate: the index then comes entirely from the page offset, which is the same in the virtual and the physical address. The L1 can start its lookup with the virtual address while the TLB translates the rest, in parallel. To grow such an L1, designers add ways (12 instead of 8), not sets.

</details>
