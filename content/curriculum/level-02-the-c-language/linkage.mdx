In Foundations you saw the linker join object files by matching names. **Linkage** is the rule that decides which names it matches. Every file-scope variable and function in C has one of two kinds:

- **External linkage:** the name means the same thing in every file of the program. This is the default for file-scope names.
- **Internal linkage:** the name is private to its own source file. You get it with `static`.

(Local variables have no linkage at all: they're only ever visible inside their block.)

## Sharing a variable with extern

To share one global between files, *define* it in exactly one file and *declare* it with `extern` everywhere else:

```c
int total = 0;       /* counter.c: the definition, which makes the object */
extern int total;    /* main.c: a declaration, "it exists, somewhere else" */
```

Both files are compiled together here. Predict the three lines:

<CRun program="c-language/link-extern" caption='One global, two files' predict />

<details>
<summary>Check your answer</summary>

`added 5, total is now 5`, then `12`, then `113`. `main.c` and `counter.c` both use the *same* `total`, because it has external linkage and there's one definition. So the `total += 100` in `main` is visible to `add`. A function declaration like `void add(int amount);` works the same way and doesn't even need `extern`: function declarations are `extern` by default.

</details>

## Two definitions, one name

Now `red.c` and `blue.c` each define their own counter, both called `count`, both without `static`:

<CRun program="c-language/link-multiple-def" caption='The same name in two files' />

Each file compiled on its own without complaint. The error comes from the linker (`ld`): `multiple definition of 'count'`. With external linkage there can only be one `count` in the whole program, and it found two. The `/tmp/cc...o` names are gcc's temporary object files, one per source file.

(Old compilers sometimes merged two uninitialised definitions like `int count;` silently. Since gcc 10 that's an error too, which is safer: two files that each thought they had their own counter would have been sharing one.)

## static keeps a name private

Add `static` to the file-scope `count` and `report` in each file, and the program links and runs:

<CRun program="c-language/link-static-private" caption='Two private counters' predict />

<details>
<summary>Check your answer</summary>

`red: 1`, `red: 2`, `blue: 1`, `red: 3`. Each file has its own private `count` and its own private `report`, so blue's count starts again at 1 and doesn't disturb red's. Only `red_tick` and `blue_tick`, which have no `static`, are visible to `main.c`.

You can see the difference in the object file. `nm` lists a file's symbols; a capital letter means external, lowercase means internal:

```
$ gcc -std=c17 -Wall -Wextra -c red.c
$ nm red.o
0000000000000000 b count
                 U printf
0000000000000027 T red_tick
0000000000000000 t report
```

`T red_tick` is shared code; `t report` and `b count` (zero-initialised data, in `.bss`) are private. `U printf` is a name `red.o` uses but doesn't define, for the linker to find.

</details>

<KeyIdea>A file-scope name is shared with the whole program unless you mark it static. Make everything static by default, and share only what other files really need.</KeyIdea>

## A private name can't be found

This program declares `log_message` and calls it. `log.c` defines a `log_message`. What goes wrong?

<CRun program="c-language/link-hidden" caption='Declared here, defined there?' />

<details>
<summary>Check your answer</summary>

`undefined reference to 'log_message'`. `log.c` defines it as `static`, so the name is private to `log.c`; from `main.c`'s point of view, no file defines a public `log_message`. Compiling `main.c` worked because the declaration promised the function exists. The linker is where that promise is checked, and it found nothing to keep it.

Fix it by removing `static` from `log_message` in `log.c` (and declaring it in a header, next lesson), or by having `main` call the public `log_twice` instead.

</details>
